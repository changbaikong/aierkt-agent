# 对话安全收口设计

## 目标

把已经复现的四类缺口一次收口：模型后备路由绕过确认或目录边界、追问后只回答参数无法续接、清空会话后旧意图残留、开场白提了旧事却没有记账。同时给管家过程事件加明确的浏览器字段边界。

## 总体方案

采用“服务端掌握决定权，模型只做有限判断或措辞”的原则：

- 路由模型只能补当前规则缺少的参数，不能改任务类型，也不能决定是否硬执行。
- 意图状态负责把追问和下一条短回答拼成一次完整请求；只有明确拒绝才撤销。
- 会话生命周期统一清理持久意图和进程内缓存，不能只删聊天气泡。
- 开场记忆拆成选题与措辞两步。选题模型最多看经过硬过滤的 6 条候选，只返回 ID 或 `null`；措辞模型最多看选中的 1 条，且不再自己申报使用了哪条记忆。
- SSE 对每种公开事件使用字段白名单，未知字段默认不出浏览器。

## 开场记忆数据流

1. 代码从用户原话和已确认事实中收集候选。
2. 代码排除低信息应答、系统过程消息、过期内容、重复内容、冷却中的线索和一次性工具命令。
3. 候选按“近期未完结话题优先、已确认高重要事实其次”排序，最多取 6 条交给选题模型。
4. 选题模型使用 `temperature=0`，只能返回 `{"selected_cue_id": "..."}` 或 `null`。服务端验证 ID 必须来自候选白名单。
5. 返回 `null`、超时或格式错误时，措辞模型在完全没有旧事内容的上下文中生成普通问候。
6. 选中 ID 时，措辞模型只看到这一条线索。它的响应只包含 `greeting`，不能覆盖服务端选中的 ID。
7. 个性化问候先按服务端选中的 ID 写入台账，再返回给前端；写入失败则返回固定普通问候。

选题提示要求优先选择近期仍可能有后续的计划、生活变化或用户主动分享的近况；排除临时查询、工具命令、普通寒暄，以及会让人感到被监视的无关细节。没有自然话题时必须选 `null`。

## 路由与意图规则

LLM 后备分类器只接收当前命中的 `_Rule`。其返回的 `task_type` 必须与该规则一致；参数补齐后仍要重新执行 `required input -> allowed_roots -> rule.hard` 三道检查。截图、系统音量等 `hard=False` 的规则永远只能返回 SOFT。

待确认意图存在时，先识别明确取消词，再尝试把短回答填进缺失参数。天气地点接受“北京”“上海市”这类短地点；音乐查询接受“周杰伦”这类短查询。无法识别的回答保留待确认状态并再次追问，不得悄悄清掉；状态仍受现有 15 分钟和 5 轮上限约束。

## 会话生命周期

`ConversationManager` 持有同一个 `IntentStateStore`，负责同时清除数据库记录和该 store 的内存缓存：

- `clear_history(scope)` 清聊天记录、播放游标、联想台账和意图状态。
- 删除会话成功后调用异步 `forget(scope)`，清意图状态并移除空闲运行态。
- 自动删除归档会话后调用 `SQLiteIntentStateStore.clear_orphans()`，删除没有父会话的意图行并同步移除缓存键。

归档但未删除的会话不清意图；恢复后仍保留未过期状态。

## 失败处理

- 选题失败：普通问候，不带任何旧事。
- 个性化台账写入失败：固定普通问候，不把未记账的个性化文本交给用户。
- 参数续接仍不完整：继续追问，不调用工具。
- 路由模型返回其他任务类型、越权目录或需确认任务：分别忽略、降级或返回 SOFT，绝不硬执行。
- SSE 未列入白名单的字段：直接丢弃。

## 验收标准

- “调一下音量”即使模型补出 30，也只能走 SOFT 确认。
- 模型补出的工作区外目录不能形成 HARD 决策。
- “查天气”后只答“北京”会执行北京天气查询；“算了”不会执行。
- 清空、删除和自动过期后均读不到旧意图，且同一进程缓存也已失效。
- 说话模型的请求中最多出现一个候选线索；普通问候请求中不出现线索和最近旧事大纲。
- 任何个性化问候都有服务端选中的合法线索 ID 和成功写入的台账记录。
- `steward.progress` 即使内部数据带 `traceback`、`error` 等字段，浏览器也收不到。
