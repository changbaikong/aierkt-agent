# 核心模块运行时与 NetEase 工具设计

## 范围

本次交付仅实现已批准的前四项设计：

1. 完善单进程 AgentLoop 使用的模块运行时契约。
2. 保持与 provider 兼容且不会冲突的模块工具命名空间。
3. 增加 NetEase 只读工具和高风险副作用工具契约。
4. 将 NetEase 播放状态作为模块私有状态持久化，而不是写入用户事实记忆。

本次不实现独立的 TTS/ASR 媒体服务、确认等待期间的会话锁、仅执行动作的恢复流程或扩展运行时事件流。这些属于后续交付项。

## 架构

`ModuleRegistry` 仍是可选能力的组合根。`ModuleSpec` 负责稳定的 ASCII `module_id`、工具构建器、provider 配置元数据、运行限制和可选健康检查。即使省略某个模块或其 provider 不可用，也不能阻止基础 Agent 启动。

注册表会为已启用模块生成一个 `ToolRegistry`。工具注册必须全局唯一。模块工具名使用现有的 `module__tool` 表示，因为连接的 OpenAI-compatible provider 禁止函数名包含点号；这样既表达了 `module.tool` 的逻辑命名空间，也不会破坏 provider 校验。

NetEase 模块包含两类工具。搜索、歌曲详情查询等目录操作属于低风险只读操作。播放、队列修改、收藏修改和切歌属于高风险 `ToolSpec`。因此，现有风险策略会在有副作用的处理器运行前创建确认请求。

## 状态与持久化

播放状态不是记忆记录，绝不能通过用户事实记忆写入器保存。专用的模块状态仓库存储 JSON 状态文档，键由 owner ID、channel、conversation ID 和 module ID 组成。NetEase 文档包含当前曲目、播放状态、队列条目和最近一次完成的幂等键。

状态写入使用 SQLite 事务，并沿用记忆存储已有的 WAL 与 busy-timeout 策略。读写都要求完整 `Scope`，因此同一用户的两个会话，或同一会话中的两个模块，都无法看到彼此的模块状态。

每个有副作用的 NetEase 请求都接受或生成幂等键。重复提交已完成的键时，直接返回已记录的成功结果，不再调用 provider。幂等键按完整模块状态键隔离。

## 契约

`ModuleSpec` 增加 provider 元数据、最大并发数、超时/限流元数据和健康检查 callable 字段。本阶段这些字段只用于声明；工具执行仍使用 `ToolSpec.timeout_seconds` 和现有风险策略。注册表提供组合根和测试所需的解析、校验辅助方法。

NetEase provider 基于协议并显式注入。工具工厂不读取环境变量，这样测试可以保持确定性，凭据也不会进入核心模块契约。

NetEase 工具返回现有规范化的 `{status, output, error}` 契约。低风险目录工具返回结构化曲目；高风险处理器只有在 provider 操作成功后才更新 NetEase 模块状态仓库。

## 错误处理

参数无效时返回失败的规范化工具结果。不可用的可选模块不生成工具，而是返回说明不可用状态的健康结果；启动不会因此中止。重复模块 ID 或重复的完整命名空间工具 ID 在注册时抛出 `ValueError`。provider 失败时不更新模块状态。

## 测试

测试会先于生产代码编写，并验证：

- 模块 ID 和命名空间工具 ID 会被校验，不能静默冲突；
- 已禁用或不健康的可选模块不会阻止其他模块组合；
- NetEase 目录操作属于低风险并返回规范化数据；
- NetEase 播放和队列操作必须通过现有风险策略确认；
- NetEase 状态对包含 `module_id` 的完整 scope 保持私有；
- 重复已完成的幂等键不会执行两次 provider 副作用；
- provider 失败时已保存的播放状态保持不变。

## 兼容性

未提供模块 ID 的现有 `Scope` 调用方继续使用 `companion`。现有工具 schema 仍符合 provider 要求。本次交付不改变既有记忆 schema 和检索行为；需要时仅通过新的模块状态仓库共享 SQLite 连接配置。
