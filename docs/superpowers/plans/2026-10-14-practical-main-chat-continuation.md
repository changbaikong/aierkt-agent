# 主聊天三项实用能力：接续实施与交接说明

日期：2026-10-14。本文是接续实施计划，不表示下列新增能力已经完成。

目标：复用已有记忆、搜索和核查，让主聊天能够记住并纠正重要决定、在长聊后保留关键背景、根据依据如实回答。只做日常够用的一版，不建设覆盖所有入口的完整系统。

执行方式：在当前会话逐项实施；接手者先读本文件及现有证据，不默认启动多个代理，不自动执行旧 B/C 计划的剩余清单。

- 已通过的给定单例是：旧“立即部署”决定 → 用户“部署方案暂时先不部署” → 后台代理主动检索并纠正 → 新空历史会话正确回答。第一次实际回答把决定误说成执行状态，修复后只复验答案一次，通过。这个成果继续使用，不重建、不重复付费跑后台。

## 范围检查与取舍

本次是三项用户能力、两组新增实施工作；它们不等于三项已发生的独立故障。

| 事项 | 性质与证据 | 当前影响 | 是否重复 | 用户可见变化与本次处理 |
| --- | --- | --- | --- | --- |
| 重要决定纠错 | 给定单例已有真实通过；决定误当执行是已修复的历史失败 | 新会话问部署决定时，能使用新决定 | 是既有 B 成果，不另开维修项 | 保持“决定暂不部署，执行情况未知”的行为；仅做已有基线回归 |
| 长聊及核查保留关键背景 | 改进建议；代码仍有核查只取最近四条用户消息、收尾主要截工具正文的规则。目标场景是否实际漏约束尚未复现 | 聊很多轮后查部署资料，较早限制可能未被核查看见 | 普通回答、搜索、重写、收尾是同一背景传递问题的表现，合为一组 | 已识别的“暂不部署”限制能一路传到回答及核查；先复现再作最小改动 |
| 当前会话疑点澄清与更新 | 代码已确认缺少连接：真实疑点留在后台待确认回执，未接成主聊天问答。不是已证明的误写事故 | 用户含糊改口时，系统现在不能完成关联明确的澄清更新 | 疑点读取、发问记录、回答关联是同一闭环，合为一组 | 先答能确定的部分，再问一个相关问题；明确回答后更新原事项 |
| 搜索有出处、失败说明、决定与执行分开 | 已有能力，扩大覆盖属于改进；本轮尚未重验所有场景 | 用户看建议时需要知道依据和是否真正做过 | 与关键背景传递共用改动，不独立重写核查系统 | 复用现有出处和失败机制，让核查也看到当前限制；仅修本场景暴露的缺口 |
| 跨会话疑点管理、后台与子代理统一、跨端接替、任意超长摘要 | 后续可选能力；当前没有本任务所需的失败证据 | 不直接影响本次主聊天综合场景 | 属于其他入口或更强能力 | 不纳入，不计为本次必须维修的缺陷 |

选择轻量接续，是因为现有保存、主动检索、搜索主循环和核查可以复用。只改提示无法把后台疑点带回聊天；执行原完整 C 则会连带改变候选排序、各类执行入口及恢复机制，明显扩大成本。只有代表场景证明现有入口拿不到必要原话时，才修那个直接阻断点，不借此恢复整套旧计划。

## 实施工作 A：关键背景贯穿主聊天

### 能力边界

- 当前问题、当前明确要求、已召回的相关现行决定及其状态，优先于可删减的旧闲聊和冗长材料。
- 本版使用已经收到的历史和已经召回的记忆；不扩大记忆检索候选、不重建排序、不承诺恢复从未召回或入口已丢失的信息。
- 保留原话及已有判断；不新增语义摘要调用，不用关键词把助手建议判成用户决定，也不从“暂时”补出期限。
- 长聊的核心保障以已保存并召回的相关决定为基础。尚未保存、未召回或只能靠隐含指代才能理解的旧要求，仍是本版能力边界，不宣传成任意长聊都不遗忘。

### 最小接口与数据传递

- 给回合请求末尾增加可选 `turn_background`，默认空，旧位置参数和旧调用继续工作。它是本轮可复用的背景对象，不是新的长期记忆库。
- 背景至少携带：当前用户原话、已经选中的记忆正文及引用、相关内容状态、待澄清事项、必要原话片段、背景缺口。消息原有编号能用就用，缺编号时只建立本轮定位，不编造数据库编号。
- 记忆会话使用现有召回结果构造背景；普通主回答继续使用现有提示拼装顺序。已经注入的同一记忆不再注入第二份，核查及收尾直接消费这一份背景。
- 已有的“决定不能证明已实施或已经停止”解释必须保留。旧记录缺判断字段时继续标明缺失，不由 C 补成确定。
- 当前用户明确改口时，本轮先遵守其明确要求；后台保存尚未成功就如实保留这个差别，C 不直接替后台改库。

### 历史与预算处理

- 输入能放下时沿用原历史；超出本次可用额度时，先保留角色与权限、当前请求、关键背景、本轮工具调用及配套回执，再从最近的完整对话组向前填历史。
- 第一版旧历史不生成摘要。已召回决定携带的必要原文留在关键背景中；剩余历史按完整组删减，不把最后几条当成完整任务背景。
- 本轮过长工具正文沿用现有缩减手段，保留成功或失败状态及截断说明；工具调用和结果必须配对，不制造孤立工具消息。
- 复用当前输入估算及整轮用量账本，调用前为实际输出和工具说明留空间；有已配置的模型输入上限时同时遵守。不要提高预算，不新建另一套计费账本。
- 必需背景本身放不下时，停止该次生成并交付已有可靠部分及具体缺口；不要静默删约束后声称完整回答。
- 不改变公开聊天历史、原工具结果或已保存记忆；删减只作用于这次发给模型的副本。

### 接入范围

只覆盖主聊天正常生成、搜索后的生成、已有核查与重写、预算收尾。给核查单独传递关键背景，普通补充背景可以继续缩短；不能再被“系统提示取头尾”或“背景截前 5000 字”裁掉关键项。

一次性要求只留本轮。现有图片及审批逻辑维持原行为，本次不改图片估算、审批恢复、代码任务或后台执行者的输入。

## 实施工作 B：当前会话的最小澄清闭环

### 疑点从哪里来

- 只读取当前账号、渠道、模块、会话范围内，由现有代理产生且有真实原话的未解决判断；不把格式错误、超时、空响应、无配置或程序核对故障变成用户疑点。
- 复用作业的 `packet`、`agent_state`、`processing_result`。第一版不把不确定内容写成普通确定记忆，不新增向量索引、不迁移生产记忆。
- 在现有作业表增加一个可选的 `clarification_state` 文本列，用 JSON 保存逐事项的问答关联；旧行缺省为空。初始化只在隔离库验证，生产初始化和迁移不在本次授权范围。
- 每项以“作业号＋原方案的事项路径”作稳定编号；多事项或 `parts` 不能只用外层 index，否则会把同轮不同疑点混在一起。
- 状态最小保留 `waiting`、`asked`、`resolved`，以及实际问题、提问回合、回答回合、解析后记录引用。原方案、原响应和原回执不覆盖。
- 每轮最多给主模型三项候选。查询最近二十条同范围待确认作业，按时间倒序读取；这是展示限额，不是语义判断。主模型依据当前问题决定是否选一项，无关事项不追问。
- 疑点原话、简短理由、已有建议问题和目标版本一并给出；建议问题缺失时主模型可以措辞，不能由程序编造语义结论。期限使用已有判断，缺失就标未知，不默认一天、不另建清理任务。

### 如何问一次而且记得住

- 增加一个主模型可按需调用的内部工具 `memory__propose_clarification`，参数仅为候选编号和问题正文；走现有工具注册及网关，候选编号由服务端校验范围及有效性。
- 这个工具只登记本轮提问草稿，按低风险、临时效果处理；不改记忆、不表示已发布。同轮最多接受一个候选，工具关闭或本轮余额不足时不另开模型调用补问。
- 主模型在现有回答流程里选相关疑点，先回答能确定的部分。程序把已登记的一个问题作为独立尾段加入待发布答案，并告知模型不要重复写这条问题。
- 搜索答案的候选及重写版本都要把这个尾段送进已有核查；普通聊天沿用现有发布规则。最终失败收口不强行附问题，不做额外澄清核查器。
- 最终确实发布的答案包含该问题，且回合成功完成后，才把它记为 `asked`。取消、超时、草稿、核查删掉的问题均不能记已问。
- 服务端发布和持久化终态是本版的记录边界；不新增“用户设备已读”回执。利用现有网页回合完成入口记录发布，不在后台生成问题时提前记账。
- 已问未答不会每轮重问。用户沉默或聊别的，保持未解决；本版不自动周期提醒，再次主动追问留到以后。用户自己明确补充时仍可解决。
- 原决定不因纯猜测自动归档；相关疑点作为附加说明呈现。当前判断需要依赖这个疑点时说明尚未确认，不能借旧决定替用户完成确认。

### 用户回答以后如何更新

- 为回合处理包增加可选 `clarification_context`，缺省空。服务端填写候选编号、原作业和事项路径、实际问题及提问回合、原始来源、目标记录和版本；不接受客户端自报的关联及原文作为可信依据。
- 同会话有未解决问题时，将当前用户原话与上述关联一并交给现有后台代理。程序只提供可能关联，是否真的回答了问题、是不是同一事项，继续由模型判断；不能把下一句用户消息自动算确认。
- 原始来源必须进入现有来源目录，保留用户原话和助手问题的不同角色；即使普通历史被裁减，也不丢掉澄清依据。助手问题本身不能证明用户采纳。
- 新回答作为一个新回合只入现有队列一次。复用主动搜索、读目标、读历史、提交方案流程，不另建第二条提炼或语义评审链。
- 模型判断仍含糊时，疑点保持未解决；用户只是聊别的时，旧决定及版本不变。明确确认同事项新决定后，才由现有写入端保存新版本和替代关系。
- 新判断和提交成功后再记录 `resolved` 及实际记录引用；失败时不标解决。其他同轮疑点不随它一起解决，原 `processing_result` 保留历史。
- 缓存、原文来源和队列内容身份要包含澄清关联。提交失败仍复用现有判断；不能为了接线而重复调用模型或产生重复版本。
- 原目标版本已变化时按现有版本规则重新读取，由代理重判受影响事项；不放宽目标版本校验。

本组只保证当前会话有范围正确的问答闭环；跨会话发现全部疑点、长期不确定记忆正式入库、云端澄清同步不在本版。

## 实施顺序与最少验证

### 接手准备

- [ ] 读取当前工作区的修改清单和以上三份证据。只记录本次触及文件的原状态，不扫描或上传密钥，不运行付费脚本。
- [ ] 用已有真实响应在临时库重放部署纠错，确认能复用当前基线。已有正确判断不重跑模型；没有复现新失败时就标为改进，不能改测试制造故障。
- [ ] 实施 A，再实施 B，最后跑综合场景；不执行旧计划的“补齐全部 B 后再做全部 C”。

### 新增离线验证限定三组

1. **背景实际传递**：早期保存“暂不部署”阶段决定，穿插六十轮固定无关对话，构造会迫使输入删减的预算。检查主回答、核查、重写及预算收尾实际收到的背景都保留该限制；检查公开历史未变。普通回复不增加模型调用。这个验证用模拟模型检查输入，不能当真实语义通过。
2. **澄清从发布到保存**：用保留的真实不确定响应验证读取；真实输出缺现代协议字段时只当兼容材料，不编造新判断。用明确标为模拟的补充响应检查提问草稿、实际发布、下一轮关联、现有写入端的新版本及解决标记。
3. **一个轻量反例组**：用户没回答而聊天气，不自动确认、不重复问、不改旧版本；同号重交不重复保存；旧位置参数和缺新字段包仍可读取。取消或失败未发布的草稿不记已问。这些是同一闭环的边界，不扩成恢复矩阵。

直接复用三条现有检查作为回归：已保存真实输出的部署重放、搜索后早期背景传递、重写后再次核查。定位在 `tests/test_memory_deployment_loop.py` 和 `tests/test_search_mainloop.py`。不要跑整库数千项测试；只有改动真的影响了其他行为，才补相应检查。

### 唯一综合真实场景

1. 临时隔离库放入明确测试种子：“部署方案已决定立即部署”。提供种子的真实测试原话，标明它不是本轮模型提炼结果。
2. 用户：“部署这事先缓一缓，后面再说。”使用真实后台判断，观察它是直接理解为阶段暂缓，还是形成有原话的疑点。明确输入不强行标不确定。
3. 如果没有形成真实疑点，保留该正确结果；仅补一个“同一提议含上线和演练，用户只回应先放着”的含糊输入，检验相关澄清。仍没有疑点则报告真实澄清未验证，停止；不反复换话术刷出预期。
4. 回到同会话：“现在这个项目该怎么安排？”主聊天先答确定部分，必要时追加一个相关问题，例如询问究竟暂停哪项；不擅自补本机地点。
5. 用户明确回答：“我说的是正式部署暂时不做，实施情况还没确认，之后再决定。”后台读取原事项及来源，保存现行暂不部署决定，保留旧版本和替代关系。
6. 注入六十轮固定无关历史，不为这些填充聊天调用模型或后台，再问：“查一下这个部署方案的准备事项，我现在应该怎么安排？”真实查询并走现有回答、来源和核查路径。
7. 对照实际回答、数据库和输入记录：仍遵守暂不部署；准备建议不冒充执行或批准；不补本机；查询结论有实际出处；无法核实的部分直说。原来的无关澄清事项不被一起解决。

如果是模拟回应或保存材料重放，证据必须标清；不能把模型“调用成功”或接口字段齐全当成问答含义正确。

## 成本、停止与交付

- 沿用已配置模型及向量服务，不偷偷切模型、用固定向量替语义排序或提高原预算。后台仍遵守每次调用 60 秒、执行 180 秒、任务 10 分钟及现有重试上限。
- 默认不新增每轮摘要、澄清判断或额外评审调用。相关疑点需要主模型登记提问时，可能多走一次现有工具步骤，计入现有用量；不宣传为完全零额外成本。
- 全部离线检查通过后只跑一遍上述综合场景，最多补一个真实含糊输入。该轮新增模型调用累计达到二十次，停止新调用并保存进展；此限额覆盖失败、重试、核查和重写，不抵消现有更小的单任务限额。
- 模型和向量调用分别记数，没有实际账单不推算金额。失败回答、空响应及未完成项都保留，不通过总分或排除失败项宣布完成。
- 某步骤失败时先用已保存原始输出定位；只修必要处，再复验受影响步骤。一次有依据的修复仍无进展就停止，不重新跑整条批次，也不不断加额度。
- 综合场景三项效果均有真实证据、三组离线检查及直接回归通过，即完成本版并收工。它是给定场景的一次通过，不代表所有记忆或所有长聊天可靠。
- 保存一份简短验收报告和一份证据文件：包含实际输入、模型原始输出、关键背景实际传递、工具轨迹、数据库版本与来源、发布问题和最终回答、失败及调用数。使用隔离路径，运行库和记忆库都显式指定，不能依赖默认项目数据库。
- 交付本次实际改动清单及必要的补丁或工作区文件，更新 `LESSONS_LEARNED.md`。B 完整依赖门槛、生产数据、云端及部署状态保持原判定；只有本版的隔离结果更新。

## 给另一模型的材料

在同一机器工作时，给它本计划路径和工作区路径即可，但必须让它检查未提交文件。换机器时，除计划外还要给当前工作树中的相关代码、现有离线测试、三份基线证据和依赖清单；仅提供 Git 提交或 `git diff` 不含未跟踪文件，会漏掉代理、协议和核查模块。

无需交付生产数据库、密钥或全部旧验收产物。无需增加其他功能清单。接手任务是把本文两组工作做成一个主聊天综合闭环；遇到超出范围的问题时先区分已有失败、建议和未验证项，只处理直接挡住这个闭环的部分。
