# B 部分维修计划：让记忆保留决策理由，并按当前问题召回

日期：2026-10-10。状态：**已有部分实现，2026-10-11 独立验收未通过**。覆盖原审计 B1—B10，排除场景对话区。原交付时为未实施；当前结果见 [B 独立验收报告](../../2026-10-11-memory-b-acceptance.md)，新版默认保持关闭。

## 目标和推荐方案

用户下一次说“这个怎么和搜索结合”时，Agent 应能找到前面讨论的具体方案、选择原因、已定约束和当前状态，再结合外部资料作判断。记忆不能只剩“用户在开发 Agent”，也不能把“建议采用”记成“已经完成”。

推荐：**回答使用的主模型在回答发布后参与候选记忆提炼，程序负责检查来源、状态、去重、权限和可靠保存；检索按当前任务选记忆。** 保留热、温、冷作为生命周期，不把分区当作内容分类或回答优先级。默认复用主回答模型配置，但提炼是另一次后台调用，必须显式传入同一回合必要背景，不会自动继承模型上下文。

不要求所有能力都改成同一种模型：向量模型继续负责把文字转换成可检索表示。主聊天候选提炼统一覆盖陪伴与项目内容，旧陪伴提炼器只保留兼容回退，不能长期在同一回合并行重复写入。

## 方案评估

| 可行方案 | 能解决什么 | 成本和长期问题 | 结论 |
|---|---|---|---|
| 只把旧提炼模型换成回答模型 | 减少模型能力差异 | 改动小，但五类陪伴限制、单轮输入和错误状态语义仍在；增加调用成本却不一定增加有用记忆 | 不作为维修方案 |
| 保留独立模型，扩展提炼输入和规则 | 可补业务记忆，后台费用可单独控制 | 输入一致后仍需双模型质量对照；模型不同本身不必然错误 | 预算受限时的后续可选项 |
| 主回答模型生成候选＋程序验证保存 | 更容易统一理解任务与形成原因，保存边界可控 | 要改回合处理包、存储语义、召回和同步；多一次后台模型费用 | 本次推荐 |
| 主 Agent 自由调用永久记忆写入 | 最灵活 | 容易把建议、网页内容或推断永久写成用户事实，回合失败也可能留下错误记录 | 不采用自由写入；只允许提交候选 |

实施成本主要在可靠输入与存储兼容，模型换配置只是很小一部分。若统一候选提炼经过样例评测后，独立模型质量相当且成本显著更低，可以更换后台模型；输入协议、校验规则和记录结构保持不变。若云端不能访问同一模型，不静默退到旧陪伴模型：先记录积压和失败，是否使用备用模型通过明确配置控制。

## 范围和先后关系

- B 负责：候选提炼、保存语义、受控可见范围、召回、历史去重、长记忆片段、业务结论入口、云本地同输入同规则。
- C 后续负责：整个主回合中角色、所有历史、工具和证据的统一上下文预算。B 只修记忆自身预算和必要接入，不重写整套上下文系统。
- D 后续负责：定时、审批恢复、快捷操作、子代理等全部旁路重新接主链。B 给业务结论统一入口，并接已有可信完成结果，不把每条旁路都大改。
- E 后续负责：云本地自动接替、租约及唯一处理端。B 提供可在任一端独立处理的同一协议和幂等写入，不让一端固定只会提炼、另一端固定只会召回，也不启用实时双端重复处理。
- A 尚未全通过，见 [独立验收报告](../../2026-10-10-search-mainloop-acceptance.md)。B 的结构和离线工作可推进；搜索融合整链验收必须先完成 A 六项收尾，不能以 B 掩盖 A 的核查缺口。

| B4 冷区受限、无关联 | 温区有结果时通常不查冷区 | 温冷均参与直接候选，再做受限一跳关联 |

## 1. 统一记忆内容与状态

保留数据库原有 `layer`（热温冷）和生命周期字段。新业务记录通过语义版本与独立内容字段区分，禁止复用旧“置信度高＝fact/confirmed”的捷径。新记录用七类 `kind`，业务状态放在独立 `content_status`，数据库 `status` 表示 active、archived、expired 等生命周期。旧记录继续走兼容读取；新查询与维护必须显式支持新记录，不能仅往元数据加字段。

| 内容类型 | 要保存什么 | 允许的内容状态与依据 |
|---|---|---|
| 事实 fact | 已发生且有来源的情况 | reported（用户明确陈述）、verified（可靠工具验证）、disputed（存在冲突）；助手说得肯定不能自动 verified |
| 决策 decision | 选择、理由、目标、被放弃选项 | proposed、accepted、rejected、superseded；accepted 只表示采纳，不表示已实施 |
| 计划 plan | 接下来要做的事和完成条件 | proposed、accepted、in_progress、completed、cancelled；completed 需要完成证据 |
| 偏好 preference | 稳定或临时倾向、适用场景 | explicit、tentative、superseded；短期情绪不能自动升为长期偏好 |
| 经验 experience | 做过什么、结果、适用条件 | observed、tentative、disputed；失败必须保留具体条件 |
| 开放问题 open_question | 尚未定义或解决的问题 | open、resolved、cancelled；“方案 A”内容缺失时记录缺口，不能补造定义 |
| 假设 hypothesis | 待验证判断、验证方式 | untested、supported、refuted；supported 仍保留假设性质，升级事实另建有依据记录 |

每条新记忆至少包括：正文、类型、内容状态、依据类别、来源引用、发生时间、所属范围、语义版本。重要决策/计划再保存 reason（为什么）、goal（目的）、project_id、topics、related_ids、supersedes（替代谁）。缺少原因就留空，不能由模型补成用户真实动机。

分开四件事：提炼把握度、来源可信程度、内容目前进展、记录是否有效。模型对句意有 0.95 把握，也不能证明事情已经完成。来源类别固定为用户明确陈述、可信工具结果、助手建议、模型推断；同条涉及多种来源时逐项保留，不混成一个“已确认”。

关系只允许指向输入中已有且有权限的记忆 ID；主题可使用少量稳定标签，先覆盖项目架构、记忆、搜索、运行部署、个人偏好等。关联不自动代表因果、采纳或授权。

## 2. 回答发布后形成统一候选

新增统一回合处理包，建议在 `agent_core/memory_turn.py` 定义并在入口、同步和 worker 复用。字段责任如下：

| 字段 | 提供者与用途 |
|---|---|
| schema_version / turn_id / occurred_at | 程序生成；用于兼容、发生时间与幂等 |
| scope / project_binding | 当前运行配置或用户明确绑定；模型不能扩大权限 |
| user_text / published_reply / outcome_status | 本轮实际请求和已发布结果；未发布候选不得冒充助手结论 |
| task_goal / relevant_history | 从主回合已有任务和必要对话取出，保留原消息 ID 与角色 |
| recalled_memory_refs | 已用记忆 ID、版本、类型、状态与相关片段，不重复传全库 |
| evidence_refs / tool_outcomes | 真正收到的网页依据及工具成功/失败状态，保留引用和证据等级 |
| completeness / omitted_sections | 哪些背景有缺口；不能因裁剪而推断“用户没有约束” |
| extraction_profile_version | 记录提炼规则版本；模型配置由各端本地解析，不上传密钥 |

默认处理包上限 8000 模型计量单位，必要历史最多 12 条/2500，已用记忆最多 10 条/1500，工具及证据摘录最多 12 条/1500，余额给当前问答与任务。按实际模型计量或保守估算；超限先去重复背景和低相关材料，不截断结构化字符串。当前问答无法完整容纳时拆分有源引用的处理单元或标为需重试，禁止静默截成已完整理解。所有限额可配置并写测试。

不传全量历史、全库、图片原始编码或工具日志；必要图片结论只能以已确认结果附引用，不能把无法读取的图片内容保存成事实。隐私过滤沿用已有规则，密钥和密码不进入记忆处理包。

候选调用在正文完成发布后由持久队列处理。默认单次超时 30 秒，最多 3 次尝试，使用可配置递增间隔；重启后可恢复，不用网页请求内不持久的临时协程充当队列。助手建议可存 proposed，但不存用户 accepted。无需每条弹确认：只有用户确实表达采纳或工具验证时，程序才允许相应状态。

回答失败或取消不保存未发布助手文本为记忆；用户明确陈述仍可按用户消息来源处理。独立可信工具成果用业务结果事件保存，不依赖一次失败回答“替它宣布成功”。模型候选失败不影响已发布回答，显示待处理/失败数量供维护排查。

同一主聊天回合启用新版时只运行新版候选流程；旧陪伴提炼器关闭该回合入口。模型返回不合规字段时校验失败或降为候选，不能把输出直接拼入数据库。

## 3. 保存、冲突与范围

采用新增字段及兼容迁移，保留原数据；建议为 `project_id` 增可索引列，其余结构化语义放带版本的元数据。所有 SQLite 查询、向量索引载荷、最终读权限、维护及同步均使用同一规则。

| 新记录范围 | 默认用途 | 读取边界 |
|---|---|---|
| conversation | 临时任务、短期情绪、未明确归属事项 | 同账号、渠道、会话和主聊天模块 |
| project | 项目决策、经验、开放问题 | 同账号及明确绑定的同项目，在允许的主聊天渠道间读取 |
| owner | 用户明确稳定偏好 | 同账号、允许的主聊天渠道；不自动开放给场景对话 |

无可靠项目绑定的业务记录先留 conversation。项目范围由程序绑定，模型给出的项目名只作为候选标签。owner 仅允许白名单的稳定偏好和用户明确授权的持久背景，默认不能把网页、助手推断或临时业务全放账号级。旧 module/shared 继续原有边界，不能把 old shared 当成“所有渠道全局”。各类范围读取先授权后精排；关联扩展也重新授权。

新业务记录不塞进 `user.task.current` 单槽，也不受旧陪伴槽位最近三条淘汰规则影响。计划状态变化不是把不相关决策逐出温区的理由。旧陪伴短期属性可保留原有效期；业务决策 active 直到明确被替代、失效或归档，进入冷区不等于结论无效。

幂等键使用账号/范围＋回合或业务事件 ID＋来源定位＋稳定语义键＋规则版本；候选先持久保存再写库，重试复用已保存候选。不要仅按“模型输出第几条”去重，换一次输出顺序不应重复造记录。同 ID 不同载荷需拒绝或进入显式版本更新，不静默覆盖。

重复内容合并引用；真正矛盾内容保留两个版本，标为 disputed 或显式 superseded。只有“改用 B、不再用 A”等明确替代依据才能淘汰 A；迟到上传、较新时间、较高模型置信度都不能自行决定最新就正确。

## 4. 让召回跟着当前问题走

检索入口接收当前问题、必要近期历史、任务目标、项目绑定和已显示的消息 ID。先判断问题是否依赖个人背景；一般知识问答不强行塞用户项目。

1. 明确的问题直接检索。“这个、上次、那个方案”先从近期历史解析指代；复杂且仍含糊时允许最多一次主模型查询改写。改写只返回查询和待确认对象，不得生成新的历史事实。
2. 先做权限限制，再对温冷区同时检索直接候选；默认每种检索路径最多 30 条，合并总候选最多 60。冷区不因温区非空而整层跳过。
3. 选最多 5 条直接相关记录，各扩展一次显式关系或共享主题，新增最多 10 条。只保留能改变判断、补原因或给有效经验的关联；没有价值不硬凑。
4. 排序顺序：当前硬约束、已采纳且有效决策、直接相关事实/计划、决策原因和经验、可选类比。内容状态与依据可信度同组内比较，时间只用于适用性和相近候选取舍，不能让近期情绪压过架构约束。
5. 主模型可对最多 20 条已授权短候选进行选择和用途说明；仅在复杂/歧义问题启用，最多一次。程序锁定权限和预算，模型不能把排序推断写成永久事实。
6. 输出正文＋类型＋状态＋原因/条件＋发生时间＋源引用及记忆 ID；假设必须显式标为未验证，已替代方案只在解释历史时出现。

保留默认记忆预算 1200 模型计量单位，但修复中文 `字数/4` 的低估：优先实际模型计量，无法取得时中文按保守每字一单位并计所有标签、引用和原因。单条默认上限 350 单位，决策的必要原因/状态可占用更多，总预算不突破。

近期历史中已有的同源内容不重复全文注入，只补语义状态或引用。长记忆不整条过滤：按当前查询选择相关片段，保留标题、类型、状态、原因、引用并标明片段；找不到相关片段则不选。相似文字但状态相反的记录不能当重复删掉。

召回本身会更新访问记录，验收仅用临时库。长期库检查不能把“真实召回”称为只读操作。

## 5. 云端、本地和业务结果接入

网页完成回合后形成同一版本处理包，进入原持久上传队列。云 API、云存储、worker 与本地提炼全部接该结构；旧一问一答上传继续接受为旧版本，但标“缺背景”，不能与新版等价宣称。

两端共享候选规则、校验规则、写入规则和完整召回能力；各端通过可信配置解析回答模型配置，记账模型标识和规则版本，不传账号密钥。同步变更带新字段，SQLite 与向量同时更新。旧端不理解新语义时隔离待升级或保留原始载荷，不能悄悄降成 confirmed fact。

同一处理包分别在临时本地库和临时云端库测试，比较状态、依据、范围、原因及引用是否一致，不要求模型措辞字字一致。默认仍只有当前指定处理端写入；自动故障接替和双端租约留 E，但幂等协议在 B 先完成。

业务结果新增统一事件适配，建议 `agent_core/memory_events.py`：源事件 ID、任务 ID、目标、真实完成状态、结论、证据/产物引用、遗留问题、发生时间及权限范围。优先接 `code_task_lifecycle.py`、`work_bridge.py` 和 `steward.py` 已有完成结果出口；进度播报及子代理口头自称成功只能为未核实来源。文件生成不等于测试通过，后台执行成功不等于用户采纳。

## 分步执行清单

每一步先写能失败的语义测试，再改最小实现；使用临时数据库与隔离工作区，保留当前未提交改动，不自动提交、推送、部署或迁移真实记忆。

### 第一步：记录契约与兼容读取

- 新增 `agent_core/memory_turn.py` 定义处理包/候选结构、版本、类型与状态校验；新增 `tests/test_memory_turn.py`。
- 修改 `memory_repositories.py`、`memory_writes.py`、`memory_postprocess.py`：新增项目字段/索引及语义校验，支持新 active 记录、稳定幂等与冲突版本，扩展维护和向量载荷。
- 不修改旧 confirmed 语义，不自动重提炼历史。新查询识别新旧两种格式；旧记录原因和完成状态未知就保持未知。
- 验证：七类状态合法性、置信度不能升级完成、重试顺序变化不重复、迟到不覆盖、升级前后旧数据可读，SQLite/向量权限一致。
- 命令：`python -m pytest tests/test_memory_turn.py tests/test_memory_writes.py tests/test_memory_repositories.py tests/test_memory_postprocess.py tests/test_memory_lifecycle.py -q`，使用项目虚拟环境。

## 最终验收样例

| 输入与铺垫 | 必须保存/召回什么 | 通过与失败界线 |
|---|---|---|
| “考虑让主模型参与记忆，因为不想陪伴和项目分裂”，之后“就按这个做，先别部署” | decision accepted、原因、计划未完成、禁止部署约束 | 回答可说已决定，不能说已经接好或已部署 |
| “方案 A 已定”，但 A 的内容从未提供 | 选择标签和定义缺口，必要时开放问题 | 不评价 A 优劣，不编造 A 内容；追问仅缺失部分 |
| 多轮讨论模型与云本地规则，随后“这个怎么和搜索结合” | 正确指代方案、同规则约束和选择原因 | 不能只搜“这个”，也不能仅列外部方案 |
| 温区有近期情绪，冷区有仍有效的“不固定按端拆能力”决策 | 冷区约束和理由优先于无关情绪 | 回答不得建议一端专职提炼、一端专职召回 |
| 超过 800 字的旧讨论，后半段才有失败条件 | 相关片段、失败条件、来源和状态 | 不整条丢弃，也不能只取开头推荐 |
| 搜索材料夸大效果，用户尚未采纳 | 外部证据独立；助手方案 proposed | 不写成用户偏好、个人事实或 accepted |
| 同项目新会话问旧选择，另项目/另账号也问 | 仅合法同项目读取 | 越权即失败；不能拿同名项目当授权 |
| 工具完成了文件生成但测试失败，后台只发过进度 | 分别记录产物事实、测试失败、剩余工作 | 不能保存“项目完成”；进度不是完成证据 |
| 云端漏回确认、本地重传；随后迟到旧方案 | 同包幂等、原发生时间、明确替代关系 | 不重复造记忆，不按上传时间推翻新方案 |
| 问通用概念，和用户项目无关 | 正常短回答，不强行召回项目关联 | 不为体现个性化而插入无关记忆 |

整链还需验证：主回答与最终核查都看到同一份必要记忆语义；入口搜与后续搜来源齐全；正确答案在事实核查后发布，正文不夹候选记忆或内部整理过程。真实模型案例建议每个关键样例重复 3 次，记录成功数及失败原因，不要求逐字相同。

## 性能、观测、旧数据与回滚

- 用户正文发布不等待提炼；后台耗时、排队时间、重试、候选数、保存数、拒绝原因和模型用量分别记录。日志只记引用、计数与原因码，不复制完整私人对话。
- 召回模型调用默认为 0，必要时查询改写至多 1、候选选择至多 1，统一计入本轮预算；提炼使用独立后台预算，不能隐藏在回答成本里。实测首字与每轮费用后再决定是否启用复杂候选选择。
- 原记录只读兼容，不凭空补原因、类型或状态。只有可引用原对话的记录才能生成离线重提候选；正式迁移先备份、抽样、比较，再经授权执行，不自动全库重写。
- 关闭新版开关恢复旧提炼/召回入口，新字段保留；新版记录不得被旧路径错误升级或维护淘汰，旧路径过滤不理解的新记录。回滚会暂时失去新版业务记忆能力，需明确显示而非谎称仍完整。
- 数据迁移使用新增列/表和版本标记，保留原文及旧键。回滚不删记录、不撤销已采纳决策、不改 Git 历史。
