**目标：** 让过程回复准确说明现在做到哪里，补齐补充搜索和原文读取的通知，减少“正准备去看看”的重复，同时避免刷屏和额外等待。

**整体做法：** 普通工具查询与回答前补充查证，共用一套当前回合的阶段通知规则。业务流程提供真实进展，通知层负责合并、限频、措辞与落库；最终回答开始交付前关闭过程通知。

**现有环境：** 保留现有 Python 后端、聊天记录数据库和网页实时消息通道，不增加第三方依赖。

## 改造依据与方案选择

已核实两个断点：普通查询仅在模型下一轮仍要工具时发上一轮证据；回答前的补充搜索与原文读取没有接入阶段通知。历史记录里存在等待约 17 秒、29 秒、100 秒却只有接手通知的回合，因此速度快不足以解释问题。这些记录包含验收任务，不能作为真实用户流量比例；等待时间也不等于模型本身的耗时。

选择统一阶段通知。只改词库成本低，但解决不了通知缺失；在每个搜索和读网页步骤里直接加消息，容易刷屏，也会让两条查询路径各自维护规则。统一方案需要一个小的通知控制文件和两处流程接入，维护成本集中，兼容现有落库和展示方式。

首版聊天过程句采用经过审核的角色化短句，并根据实际动作和已确认信息组合，不为每句进度再调用模型。理由是当前措辞生成被流程直接等待，可能额外等到三秒；通知内容短且阶段明确，本地生成更容易控制事实与耗时。后台任务原有的角色化通知保留，后续若确实需要更自由的过程表达，再单独评估后台改写，不扩大这次范围。

## 体验规则

| 实际情况 | 通知条件 | 允许的表达示例 |
| --- | --- | --- |
| 第一次查询正在执行 | 连续查询等待达到 1.5 秒且任务仍未结束 | 我在查资料，先看看能找到什么。 |
| 搜索已返回材料，还要继续处理 | 结果确实存在，下一步明确为筛选、补查或读取 | 搜索返回了几条材料，我再核对一下。 |
| 确实开始读取原文 | 已选定可读来源并开始读取，尚未取得正文 | 我在读原文，核对里面的说法。 |
| 已取得原文，但仍要读其他来源 | 正文已成功取得，且下一次读取确实会执行 | 这份原文已经取回来了，我再看看另一份。 |
| 第一条线索为空或读取失败，确实换路 | 替代搜索或读取已决定且有剩余预算 | 这条线索没提供足够材料，我换个来源看看。 |
| 资料互相矛盾 | 已识别具体矛盾，且还会执行补查 | 两份材料的说法有出入，我再核对一下。 |
| 即将直接交付结果 | 没有后续查询或读取 | 不补过程句，直接给最终回答。 |

这些例句仅示意阶段含义，实施时配套同阶段的多条角色化短句。不能把“搜索返回材料”说成“已经确认答案”，不能把“读取开始”说成“看完了”。发现矛盾但没有进一步查询预算时，应在最终回答说明，而不是承诺继续核对。

首版默认规则自行确定，后续根据实际体验调整：

- 快速回合：从首次实际查询开始到最终交付，不满 1.5 秒不发过程气泡。普通闲聊和已有零等待的只读回复不增加气泡。
- 有真实阶段变化才能发消息；时间只决定是否值得通知，不能凭时间制造进展。长时间单次查询可以只有查询中的通知和最终结果。
- 相邻过程消息至少间隔 4 秒。间隔内的新进展覆盖待发旧进展，到期只发当时仍成立的最新状态。
- 一次聊天回合最多一条接手通知、两条中段通知。不要求凑齐三段，不按每个网页、每次重试分别播报。
- 如果第一次通知前已进入读取，就直接说正在读原文，省掉已经过时的接手通知。
- 等待用户确认等必须告知的消息保留现有即时规则，不受普通查询通知上限限制。
- 最终回答、取消或失败收口前关闭通知；旧回合不得在最终回答之后补发进度，也不得串到下一轮。
- 过程句不额外调用模型，不人为延时业务执行；消息落库和广播仍走现有通道，实际存储耗时单独观测。
- 同一会话保留最近三条已发布过程句作为本地选句依据；同阶段优先选近期未使用的短句，不把旧对话送入生成提示。
- 不把网页正文、文件路径、查询参数、内部错误或模型推理直接放进过程气泡；阶段信息通过公开、安全的摘要表达。

## 实施任务

### 任务 1：建立可验证的通知规则

输入是一条可信的阶段记录：本回合身份、阶段、已确认摘要、当前动作、是否还有后续工作、实际查询开始时间。输出是发送、暂存合并或跳过的决定。阶段记录禁止包含原始网页正文和内部异常。

- [ ] 先写行为测试，使用可控制的时钟：查询在 1.4 秒结束不发消息；到 1.5 秒仍在执行才通知；4 秒内多次变化只保留最新状态；中段超过两条不再发布。
- [ ] 验证关闭后永远不发送；回合 A 的待发消息不进入回合 B；不同会话的选句记录和去重信息隔离。
- [ ] 实现独立的本回合通知控制文件，队列最多保存一个最新状态。需要延后通知时启动可取消的轻量等待；查询、读取与最终生成继续执行。
- [ ] 为重复阶段使用稳定的逻辑节点身份，例如本回合的首次材料、原文读取、改道；不得用每次随机工具编号绕过去重。
- [ ] 在最终交付前先禁止新通知并取消待发通知；已进入落库的通知要完成有序收口，再交付最终回答，防止最终后补发。不能只取消一个等待任务就假定竞态已消失。
- [ ] 运行新文件的测试，确认发送时检查的是最新状态，而不是等待开始时的旧状态。

### 任务 2：先修普通查询的阶段与证据

输入是实际工具结果及已决定执行的下一步。输出是安全阶段记录，不允许用“没有抽到摘要”代替“搜索没有结果”。

- [ ] 先增加反例：成功结果只有嵌套材料列表、没有顶层标题时，不能误报“没有找到”；只有查询词、零条结果或失败状态时，不能当成取得证据。
- [ ] 对常见搜索和正文读取采用明确的结果结构判断。未知工具只使用已确认的安全摘要，不能把任意字段当成事实，也不能把本机路径说出来。
- [ ] 第一次实际查询开始时报告当前动作；搜索返回且确实还有下一步时报告取得材料；读取开始与成功取得正文分别判断，不能提前宣称读完。
- [ ] 普通查询结果已足够、模型直接最终回答时，不强加“找到材料”的中段。若模型继续查询，明确填写实际下一步，避免通用的“继续手上的事”。
- [ ] 将这条路径的普通查询通知交给统一规则，避免旧触发点和新触发点各发一次。
- [ ] 更新已有“工具前一定发接手句”的测试要求，改为长回合、快速回合分别验证；保留顺序、事实边界和后台任务通知测试。

### 任务 3：补齐补充搜索与原文读取

输入是回答前补充查证的现有搜索计划、返回材料、实际读取计划及剩余预算。输出与任务 2 一样的阶段记录，不改变查证决策。

- [ ] 先增加反例：长回合多次补查后只有接手消息；已经取得材料但通知仍说准备搜索；原文读取未成功却说已看完。
- [ ] 补查开始时报告正在查证；每次结果返回后先按原规则决定是否继续，再报告取得材料或改道。只在下一次查询确实会执行时承诺继续查。
- [ ] 开始读取首份原文时报告读取阶段；读成功且还有下一份时报告取得正文并继续读取。第二份原文不自动多发一条消息，由合并与上限规则决定。
- [ ] 网页与视频详情读取共用公开阶段表达。工具不存在、预算用完、空结果或失败时，没有替代动作就进入最终说明，不许发送“正在换来源”。
- [ ] 已由模型取得的材料和补查取得的材料共享通知次数和逻辑节点身份，避免补查重新发送接手消息、清零限额或重复说找到材料。
- [ ] 用现有多来源、搜索预算、平台失败和流式回答暂存测试回归，确认搜索次数、来源范围、最终答案和原有交付时机没有被通知规则改变。

### 任务 4：让句子有阶段感，处理重复与公开边界

输入是经校验的当前动作与有限证据。输出为一条不超过 60 字的公开过程句，不新增模型调用。

- [ ] 给查询中、取得材料、读取中、取得正文、改道各准备至少四条短句；保持现有人物语气，避免客服腔，不照抄用户长问题。
- [ ] 在会话最近三条已发布句子之外选用短句；去重依据只影响选择，不加入气泡，也不进入模型提示。近期记录内存有界，按会话身份隔离，重启后不强求恢复选句历史。
- [ ] 已取得材料与读取中的句子不得退回“刚打算”“正准备开始查”。不允许固定地附加“关系不清楚”或“需要再查”，除非当前阶段确实有这个原因。
- [ ] 继续使用公开文字校验；无有效摘要时说当前动作，不把查询词、检索结果数量或标题当成已经证实的答案。
- [ ] 若新增读取阶段，验证网页事件公开字段、聊天历史和现有展示都接受它；默认复用已有过程消息外观，不新增前端动效或播放器。
- [ ] 验证选句、通知控制、落库或广播失败时主任务仍可继续，内部错误不进入气泡；后台完成、审批、失败等原有通知不被聊天专用规则误改。

- [ ] 为最后一条通知与最终答案几乎同时到达增加竞态测试：数据库顺序、即时事件顺序与刷新后顺序一致，不出现最后答案后又说“正在查”。
- [ ] 验证取消、失败、异常退出和下一回合开始时，待发通知都能停止；重复回调不会产生重复气泡。

- [ ] 对照记录实际业务阶段、已发消息、总等待和模型调用次数：阶段准确、通知不增加模型调用、不额外等待；单元测试只能证明控制规则，不能代替真实网页体验。

## 验收场景

| 场景 | 必须出现的行为 |
| --- | --- |
| 普通闲聊、快速只读查询 | 直接最终结果，不增加过程气泡和模型调用。 |
| 1.4 秒内查询完成 | 零过程气泡，最终结果不被人为延后。 |
| 查询持续 10 秒后直接回答 | 有准确的查询中通知；不为长耗时强塞取得证据或读取阶段。 |
| 慢查询取得材料后继续读原文 | 中段表达取得材料或读取中，不再说刚准备搜索。 |
| 多关键词、多来源补查 | 真实进展被通知；同一回合最多两条中段，四秒内只保留最新状态。 |
| 两份原文连续读取 | 成功取得正文与仍在读取区分清楚，不每读一份都刷屏。 |
| 零结果但有后续查询 | 只说改道，不说找到了。 |
| 结果有材料列表却没有顶层标题 | 不误判为空；也不因有标题就宣称答案已确认。 |
| 读取失败、没有替代路线 | 不承诺继续查，最终如实说明限制。 |
| 发现冲突但预算已经用尽 | 最终说明分歧，不制造正在补查的状态。 |
| 正文完成、最终生成仍在进行 | 未取得新进展不反复报相同状态，也不编造“正在核对”。 |
| 取消或最终回复与通知同时发生 | 终态后零过程消息，下一轮不串入旧句。 |
| 连续多轮查询同一阶段 | 优先避开最近三条句子，阶段含义仍准确。 |
| 通知通道故障 | 主任务继续，失败不转成内部错误气泡。 |
| 后台任务完成、等待用户确认 | 保持已有必要通知与身份隔离规则。 |

## 风险与交付顺序

最大风险是延后发送时阶段已经过期，以及最终回答与通知同时落库。任务 1 必须先把“发送前读取最新状态”和“终态关闭”验证好，再接入两条业务路径。第二个风险是目前搜索代码有其他改动，实施时应以最新的实际结果结构为准，避免复制旧流程。

按任务 1 至 5 顺序在当前会话内实施，完成一项就验证对应行为；不引入额外代理或新的后台任务系统。1.5 秒与 4 秒是首版体验参数，不作为进展真假判断；若真实入口显示消息太稀或太密，只调整这两个参数，不改变事实规则。

最终交付应包含：普通查询与补查两条路径的改动、阶段短句、自动测试结果、真实网页观察结果及尚未完成项。本计划完成不代表行为已经修复。

## 补充范围：代码代理长任务的管家式进度

代码代理应纳入改造。它的内部工具循环运行在独立执行进程里，不能依靠主聊天模型再次调用工具来触发中段。现有执行层已经发出工具活动和补丁等事件，但聊天回传仅处理完成、失败、取消、中断及等待审批；这是需要补上的另一处断点。

复用统一通知的合并、公开措辞和去重能力，但区分两种生命周期：普通查询跟随聊天回合关闭；代码任务跟随任务及执行尝试关闭。主聊天回复“已经交给代码代理”不等于代码任务终态，不能关闭其通知。后续进展写回最初发起任务的会话，用户在该会话继续说话也不改变任务归属。

## 后续改造：措辞改为动态生成（2026-10-09）

**目标：** 阶段通知的"说什么"继续由程序判断，"怎么说"交给模型；固定短句库从主路径上彻底退场。

**已实现**

- 删除 `CHAT_STAGE_LINES` / `WORK_STAGE_LINES` / `STAGE_LINES` / `ChatStageNarrator`（选句器）及其选句测试；新增 `RecentPhraseMemory`（同一会话最近三句已发话术，只做去重输入）与 `StagePhraseGenerator`。
- `StagePhraseGenerator` 只收安全的人类可读信息：目标摘要、当前阶段、确实会执行的下一步、可公开的事实摘要、最近已发过程句。工具名、文件路径、命令、异常、正文全文、模型推理都不进提示词。
- 生成结果仍走 `steward_line_issue` 公开校验，并新增近期重复检查（指纹相同 / 互相包含 / 字符二元组重合 ≥0.7）；生成失败、超时、不合格或重复 → 返回空串，**这一条直接不发，不回退固定句**。完成 / 失败 / 取消 / 等待确认等必要通知保留原有兜底模板。
- `TurnProgress` 拆成两段：`compose` 在后台任务里生成（可取消、短超时），`emit` 才落库广播；主任务只 `await note()` 排队，不等措辞。交付最终回答 / 取消 / 终止时先取消未完成的生成，生成完成后还有一道**发布闸**再看一次是否已关闸。节奏改为按**真正发出去的时刻**计算。
- 阶段报告补上安全事实：`steward_progress.STAGE_FACTS` 给每个阶段一组结构性事实（摘要 + 下一步），调用方可以覆盖，但它们只是措辞输入，不会被原样发出去。
- 普通查询、补充搜索、原文读取、代码长任务四条路径共用同一个生成器；任务身份与终态关闭规则仍按聊天回合 / 执行尝试分别隔离。

**失败行为（明确写下来，避免以后退回模板）**

- 只有"必须告知"的通知（等待确认 / 完成 / 失败 / 取消 / 中断）继续使用原有兜底措辞。
- 关闸时会先让出一次事件循环：给"已经到点、只是还没被调度到"的那条一个机会；措辞还在路上的一律取消，绝不等待。
