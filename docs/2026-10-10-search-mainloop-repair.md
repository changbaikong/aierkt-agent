# 联网搜索回主回答链：实施说明（A1—A8）

对应调查报告：`docs/2026-10-10-main-agent-context-audit.md` 的 A 部分。
本次只修 A 部分；B（记忆提炼与召回）、C（上下文统一编排）、D（其他旁路）、E（云本地对齐）不在本次范围。

> **复验更正（2026-10-10）**：下文保留实施记录及当时脚本结果；本次独立验收确认核心接链成立，但完整验收未通过。实时脚本的 13 项 PASS 含图片理解、未定义方案等薄弱断言，不能作为完整通过依据；另有六项已复现缺口。当前结论和收尾条件见 [A 独立验收报告](2026-10-10-search-mainloop-acceptance.md)。

## 一句话结论

搜索不再是一条"另起一个回答器"的分叉：入口判定需要外部事实时，先按预算取证并把**整理后的事实**作为工具证据放回主回合，
由同一个主 Agent 带着角色、记忆、历史、图片和一次性要求综合作答；正文只在最终核查通过后发布一次，来源走结构化字段。

## 改了什么

| 任务 | 位置 | 做法 |
|---|---|---|
| 一、取消独立搜索回答出口（A1/A2/A3） | `agent_core/loop.py` | 取证结束后回到 `_continue` 主循环；删除只接最近四条历史的 `AnswerComposer.compose` 与整套"门代查 → 独立重写"链 |
| 二、材料整理成任务相关事实（A4） | `agent_core/search_orchestrator.py`、`agent_core/search_gate.py` | 覆盖检查与事实整理复用同一次调用：返回关键事实、来源编号、适用条件、未覆盖问题；原文按段落选取，保留后半段限制条件并标记截取 |
| 三、统一表达与最后核查（A5/A6） | `agent_core/answer_composer.py`、`agent_core/loop.py` | 删除"一到三条关键依据"；最终核查同时看证据支持、摘要/原文级别、冲突、用户要求是否被回答、材料堆叠与内部话术；**另加一道确定性排版检查**：简单问题出现两个以上加粗小标题/要点清单就重写一次；重写后再核查一次，第二次不过走安全收口 |
| 四、入口误判可纠正（A7） | `agent_core/loop.py`、`agent_core/search_gate.py` | 删掉"已有入口判断就跳过回答前检查"；判定失败记成"未确定"；每回合最多补搜一次，补搜后回主循环重答；入口/模型/补搜共用一本预算账 |
| 五、统一发布、用量与耗时（A8） | `agent_core/loop.py`、`agent_core/turn_timing.py` | 正文核查通过后一次性发布（不再按 32 字符模拟）；首字时间从回合开始计；判定、整理、主回答、核查、重写全部记账，缺用量标"估算"；快照不再写零用量 |

### 新链路顺序

1. 主回合组装角色、记忆、历史、图片、一次性要求（原样保留）。
2. 入口判定：闲聊/情绪/创作/本地操作零搜索；事实与时效问题直接取证。
3. 取证：网页（博查+Bing）/B站，按需读原文；整理成事实（来源编号、证据级别、适用条件、冲突、未覆盖问题）。
4. 事实作为**成对的工具消息**（assistant tool_calls + tool 回执 + 证据约束）进入主回合。
5. 主 Agent 继续用允许的工具综合作答；搜索与读取用完预算只关这两类能力。
6. 最终核查通过 → 一次性发布正文 + 结构化来源；不通过 → 重写一次 → 再核查 → 仍不通过则安全收口。

## 整轮预算：35000（主回答链与辅助调用共用一份）

按实测把整轮上限从 12000 提到 **35000**，并且**辅助调用与主回答链共用这一份**：

| 场景 | 实测整轮（输入+输出） |
|---|---|
| 简单事实问题（1 次搜索） | 约 9,800 |
| 两次搜索（含 3–4 次材料整理） | 13,500–19,900 |
| 带长期记忆、答案被核查打回重写一次 | 约 30,900 |

12000 只在"主回答链"口径下勉强够用：一旦辅助整理花掉几千，主回答就没额度了（这正是上轮复跑失败的场景）。
35000 既覆盖最贵的实测回合，又让"整轮不超过上限"成为真上限 —— 辅助花掉的会从同一份里扣；
用尽时按已核实事实收口，不会硬发一个注定被截断的请求。

后台定时任务也改成同一份口径（`task_service` 里的 `TURN_TOKEN_BUDGET` 取自 `AgentLoop.MAX_TOTAL_TOKENS`，
不再各自维护 12000）：后台任务同样走联网取证与核查，用旧口径会在长任务上过早收口。

## 验收结论（第二轮收尾后）

工具重跑会发现一个取舍，这里写清楚：**整轮上限 35000 由主回答链与辅助调用共用**。
第一版收尾时把辅助用量从主循环额度里扣，但上限还是 12000：记忆会话回合（一次问题触发 3 次覆盖整理、
约七千 token）在系统提示本来就长的情况下算不出可用额度，主回答一次都没发出去，整轮退化成安全收口。
**把上限提到 35000 后，共用一份的口径不再会饿死主回答**（实测最贵回合约 30,900），
同时"整轮不超过 35000"仍然成立；辅助调用各自在调用前用 `_aux_budget_left` 守预算、调用后结算。

四场景实测要点（第三次跑通的那一版）：
- ① 摘要式回答，标出"各来源对定位说法不一致、收费与系统要求查不到"；
- ② 明确说"你的项目细节我这边只有『本地聊天 Agent、预算五千、已选定方案 A』……也不能替你认定方案 A 就等于某个工具"，并请用户补全；
- ③ 读出图内文字（安装代号 KESTREL-7、本地运行、兼容 OpenClaw），同时提醒"图上的说法在查到的安装资料里没出现，别照着装"；
- ④ 给出租金信息并标注非官方口径，拒绝在没有用户反馈的情况下下"值不值得买"的结论。

核查器现在会拿到用户本轮的图片（与主回答同一张），因此"回答对图片的描述"能被核对，不会因为外部证据里没有就被判不合格 —— 这一条是 ③ 之前反复失败的原因。

仍不在本轮范围：网页历史气泡与主舞台来源位置的浏览器验收、生产云端版本与真实记忆库的融合验收；
Jina 原文读取在本机经常 20 秒级超时，属于体验问题，不改变"失败如实计数"的口径。

## 保留的口径

- 搜索门开关（`SEARCH_GATE_ENABLED=false`）仍表示"恢复旧流程"：入口判定、漏搜纠正与最终核查都不介入。
- 每回合最多 3 次检索、2 次原文读取；失败与空结果同样计数。
- 外部搜索词只含取证必需的对象和条件（单行、限长），不把个人记忆或完整历史发给搜索网站。
- 真实验收不得把测试标记写入用户长期记忆。

## 独立验收后的收尾（第二轮）

第一次独立验收（`scripts/verify_search_mainloop_acceptance_edges.py`，退出 1）指出六项缺陷，已逐项修复：

| 缺陷 | 修法 |
|---|---|
| 1 后续搜索证据没汇总 | 回合证据只有一个出口：入口整理的 `EvidenceBundle` 与主循环里模型自主检索/读取的回执统一合并、按网址去重、来源编号接着已有编号继续编；未整理的后续材料标 `snippet`/`original` 等级，不升级成已核实事实。核查与交付来源共用这一份。 |
| 2 核查缺任务背景 | 核查背景改为：角色/记忆取**头尾**（长记忆尾部不再丢）、最近四条用户要求（含较早约束）、本轮非搜索工具结论；被预算省略的部分明确写"背景缺口"。 |
| 3 失败路径转述未核实摘要 | 安全收口不再回退到原始摘要：没有已核实事实时只说明无法确认、具体缺口，并写明已有材料未核实、不作为结论；有事实时只用已核实条目。 |
| 4 辅助调用绕过预算 | 入口判定、材料整理、核查、重写全部走调用前预算守卫；主循环剩余预算统一扣除辅助用量；预算不足时按已确认事实收口并记 `budget_stop`。 |
| 5 用量漏记/被估算替代 | 判定与整理的用量解包成**原始 usage**（不再套一层 `{"usage": ...}`），入口判定在搜索路径同样入账；主回答缺用量时按真正发送的消息与产出内容估算并标"估算"。 |
| 6 长答案尾部未核查 | 核查不再截断候选答案；结构化证据按字段预算（事实 8×400、来源 12、材料 6×400、背景 4000），超长回答按 6000 字符分段核查，任何一段不通过即整体不通过。 |

另修：`test_timestamps_in_rows_feed_freshness` 不再写死日期；实时验收脚本的图片改为可读 ASCII 并带图内独有标记 `KESTREL-7`（缺图记为"未验收"而不是通过），正文只发布一次改按事件时序断言，并接上网页管家核对"进度在前、正文在后"；覆盖检查的 `missing` 只允许写外部事实缺口，不再把"用户预算"这类个人情况列成缺失的外部事实；核查背景额外按 `[CONFIRMED_FACT]` 等标记整段抽出记忆（记忆被组装在提示中段，只取头尾会正好跳过它）。

## 真实记忆链验收

`scripts/verify_search_memory_chain_live.py`：临时记忆库 + `MemoryAgentSession`，走"召回 → 搜索 → 主回答 → 核查 → 发布"整链，
不碰生产记忆文件、不启用提炼与云同步。11 项检查全部通过，实测回答同时使用了召回的个人背景与外部证据：

> 查到了，但说实话材料里没写你 plan A 具体是什么，我只能按"五千预算、本地跑聊天 Agent"这个前提说。…… 五千块这个预算，钱基本该花在内存和显存上，模型本身不花钱……具体选哪个尺寸的模型，得知道你 plan A 是打算跑多大的。

（召回层、主回答输入、核查背景三处都验证到记忆标记；2 次检索、6 条结构化来源、正文只发布一次且进度在前。）

## 仍属 B—E

- B：记忆只保存陪伴属性、检索只按当前话语、冷热区优先级与重复占用（搜索回答现在能用到已召回记忆，但不承诺修好漏召回）。
- C：没有唯一的回合上下文对象；长历史收口、优先级排序与角色/证据契约仍未统一。
- D：定时任务、子代理、代码任务、审批恢复、命令行与快捷播放/导航旁路仍各自拼上下文。
- E：云端与本地仍是"本地记录、云端异步提炼"，没有主端/接替端协议与回合级去重。
