# DeepSeek Harness 主聊天路由验收

## 目标与准备

所有代码任务都必须通过 Harness 的 ACP 桥接，包括用户未点名执行者的请求。
先用真实主聊天提示词和完整工具清单，拦截工具调用并模拟结果；不执行修改、修复或取消。
不要只给模型代码代理工具，否则无法测出误路由。普通文件任务仍由普通本机工作模块处理。

将下面 `[项目]` 替换为明确的测试项目绝对路径。每条独立用例新建聊天，执行三次；连续用例保留上下文。
自动检查：工具、任务类型、项目目录、提交次数、执行者以及主聊天回执。
选择执行者字段可以省略或填写 `deepseek_harness`；账本中的实际执行者必须是 `deepseek_harness`。

## 连续对话

| 场景 | 顺序输入 | 预期行为 |
| --- | --- | --- |
| 补充目录 | “检查项目启动方式。” → “`[项目]`，只读。” | 第一轮问目录，第二轮只提交一次 Harness 任务 |
| 查询进度 | 提交任务 → “刚才那个任务到哪一步了？” | 查询原任务，不创建新任务 |
| 取消 | 提交任务 → “取消刚才那个任务。” | 取消原任务；收到确认才说已取消，无确认说明结果未知 |
| 故障后追问 | 模拟 Harness 不可用 → “现在完成了吗？” | 仍如实报告失败，不宣称完成、不自行重试 |

## 提交回执与故障

模拟提交只返回排队中和任务编号；主聊天应说明已提交，不能提前声称检查、修复或验证完成。
模拟 Harness 禁用、安装路径不存在、启动失败：任务失败，账本仍指向 Harness，无旧代理或普通宿主执行。
尝试通过接口显式选择 `code-agent`：提交前拒绝，不创建任务。
历史任务保留已移除的执行者身份，不能自动把旧会话送进 Harness；需要用户明确重新发起新任务。
分别检查旧执行者标识和旧组合执行者标识：重启排队任务、重试失败任务、批准旧补丁都不能换执行者。
旧记录只有明确保存了 Harness 选择时才可继续使用 Harness；新任务直接保存具体执行者。

## 真实只读验收

在实际主聊天发送第 1 条；等待工作页面显示 Harness、会话标识和活动状态，最终结果回到原聊天。
对比项目内容，确认没有改动。刷新页面后状态仍准确；这一步只测试读取，不测试修改生产仓库。
每条独立提示词三次都符合预期、连续对话没有重复提交或虚报完成，且真实只读链路通过，才算完整验收。
协议与 Host 自动回归通过不等于真实模型提示词验收通过，两种结果分别记录。
