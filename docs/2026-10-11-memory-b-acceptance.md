### 双端走真实 HTTP 的闭环（本轮新增，并因此查出一个真问题）

新增 [verify_memory_dual_end_http.py](../scripts/verify_memory_dual_end_http.py)：云端 API 起在临时目录（`cloud_memory.api:app`，鉴权用临时口令），本端用真实的同步客户端与同步器；四段全走真接口 —— 上传经 HTTP 落进云端队列、云端工人处理、本端拉变更合并、纠正再来一遍。**8/8 通过**，退出码 0。

- 上传：回合经 HTTP 被云端接收并落库；错误口令的拉取被拒（401）。
- 处理与回传：云端落成新语义记录，本端拉到并写进本端库。
- 纠正：云端把三千落成第 2 版现行版本；本端拉回后现行版本是三千，旧的五千归档为 superseded 并指向新版本，本端召回到的也是三千。

**这一步查出的真问题**：云端接口收上传时用的是 `TurnPayload`，它当时**没有 `packet` 和 `schema_version` 两个字段**。本地上传本来是带着处理包的（多轮决策过程、本轮用过的旧记忆引用、可信项目绑定都在里面），pydantic 把多余字段静默丢掉 —— 云端于是永远只看到一问一答，**更新建议没有可指向的旧记录，纠正与替代在云端整条失效，而且不报任何错**。修法是接口把这两个字段收下并落库；对应用例 `test_the_processing_packet_survives_the_upload_hop` 钉住它。

## 自动记忆维护闭环改造计划

补充日期：2026-10-11。最新状态：**已有实现；原 11 项及第一轮 6 项反例在第三轮再次通过，但新增 7 项变体失败，真实模型本轮因余额不足未能验证，完整验收不通过**。以下保留原实施任务和完成条件；纳入 B 的保存、更新和验收范围，场景对话、全局上下文编排及双端自动接替仍按原 C/D/E 范围处理。

### 目标、架构与执行边界

**目标：** 正常聊天即可自动形成有价值的记忆；新信息能补充、纠正、替代旧记忆，后续回答使用更新后的内容。用户无需逐条下达保存指令，也无需为了入库专门确认。

**架构：** 在现有 B 持久队列、候选提炼和保存规则上增加内容更新任务。模型一次提出候选、保存价值及更新建议；程序核对真实来源、权限、目标版本和实际写入结果。现有冷热迁移、到期处理和检索数据维护继续承担生命周期工作，新增内容维护与它们协调，不另造一套互相冲突的记忆库。

**技术基础：** 复用当前 Python 服务、SQLite 持久存储和现有向量检索库。执行本计划时逐项采用 executing-plans 技能检查实现与验证结果；写入原计划不授权自动提交、推送、部署或改生产数据。本轮是独立复验。

共同约束：

- 自动保存与“用户已采纳”是两个判断。明确陈述、偏好、约束以及值得保留的建议均可自动入库，但保存时保留来源和状态；不把用户确认设为所有记忆的入口条件。
- “嗯”只针对上下文中能够明确定位的对象判断；明确认同可记录为认同，多个建议混在一起或指向不清时保持待定，不为保存强行追问。
- 没有下一条回复，不影响当前回合的保存。既不要求产品提供已读回执，也不把已读、沉默或未反对当成采纳、实施或完成证据。
- 原始对话是出处，不把全部聊天压成长期事实；仅提取能影响未来回答的事实、偏好、约束、决策、计划和经验。临时情绪保持短期语义，普通寒暄可不生成长期记录。
- 模型自检只能提供检查建议；原消息、真实工具结果和写入回执才是核对依据。模型重复同一判断、输出更高置信度或自己说“检查通过”都不能提升事实状态。
- 每次变更先验证来源与完整权限，再判断语义。保留必要出处、变更原因及历史版本，发生冲突时不按上传时间或置信度自动选真相。
- 两端共用同一内容维护规则，同一回合或维护任务只由指定端处理；跨端接替仍不在本次范围内。

### 已有能力与新增能力的分工

| 能力 | 当前已有基础 | 本次新增或修正 |
|---|---|---|
| 自动保存 | 旧提炼和 B 候选写入入口 | 同一回合自动处理有价值信息，不等下一次用户回复；同时修复 B-R1、B-R2、B-R11。 |
| 同类新旧处理 | 旧槽位替换、新语义来源合并和替代字段 | 区分补充、纠正、真正替代与冲突；依据源证据生成版本，避免简单“最新覆盖旧”。 |
| 定期维护 | 冷热迁移、过期清理、检索数据更新 | 增加有界的内容检查任务，仅针对到期复核、受影响或有未解决冲突的记录。 |
| 读取与召回 | 温冷共同候选、关联扩展 | 默认用有效的新版本，冲突显式展示，旧版本只在解释历史时使用；所有路径遵守范围与开关。 |
| 写入后检查 | 基础写入、检索补偿和同步接口 | 核实写入后的内容状态、版本、来源和同步变更；部分失败分别记账，不能假报整个更新成功。 |

### 更新动作与状态规则

每项更新建议带上：来源消息或事件引用、目标记忆编号、预期目标版本、动作、新内容、内容类型与状态、原因及发生时间。新建不需要目标编号；其余动作必须指向本次已授权输入中的记录。模型返回的范围、来源角色和版本均不能直接作为授权依据。

| 动作 | 触发依据 | 落库与后续回答行为 |
|---|---|---|
| 新增 | 有价值且未存在的明确内容，或值得保留但尚未确认的建议 | 按真实来源保存；助手建议保持 proposed（待建议状态，尚未采纳），模型推断保持未验证。 |
| 合并或补充 | 同一事项出现新原因、条件、出处或其他相容细节 | 生成可追溯的新版本或追加来源；保留原有状态，不能因合并升级为已完成。 |
| 纠正 | 用户明确指出旧陈述错误，或可靠结果推翻具体旧结论 | 新版本记录纠正内容和依据，旧版本退出当前有效集合；原本只有用户陈述的内容仍保持 reported（用户陈述，尚未核实）。 |
| 替代 | 对明确对象表达“改用 B、不再用 A”，或可明确定位的选择变化 | 保留旧选择及形成原因，新选择成为现行版本；不把改了计划记成已经实施。 |
| 标记冲突 | 两条可信陈述互相冲突，但时间、范围或条件尚不能解释 | 保留双方及冲突关系，不擅自择一；回答涉及此事项时说明不确定性。 |
| 失效或待复核 | 明确到期、取消、被替代，或可靠新证据显示不再适用 | 依据具体理由处理状态；长期项目原则不能仅因较旧或较少访问而变成错误。缺出处时标记待核对，不凭空推翻原内容。 |
| 保持或忽略 | 内容已完整存在、变化无价值、仅重复寒暄，或**无法逐项写明缺哪条证据、下次从哪里取证** | 不生成重复记忆；需要等待证据的事项必须记录具体缺哪条证据与取证的路径，不反复调用模型“猜答案”。 |

“允许自动保存”不等于允许自由扩大可见范围。长期稳定偏好才按原规则进入账号范围；无可信项目绑定的事项继续限于会话。过期和历史清理沿用原保留政策，模型维护动作不直接授权批量删除。

### 触发、预算与可靠处理

**逐轮触发：** 回合正文发布后，使用同一回合号将必要对话、新候选和相关旧记忆交给指定端队列。用户已说出的有价值信息在回答失败或取消时也可处理，但未发布助手文本不得作为已发生的助手结论。业务结果通过现有可信事件入口触发，不能从播报措辞猜任务成功。

**定期触发：** 复用现有维护运行器安排内容检查，默认每 30 分钟挑选一批，最多 20 条；只取明确设定的复核到期项、新证据影响项及待解决冲突。检查时间到达只表示需要评估，不等于内容自动过期。没有候选直接跳过，不重读全库、不发起模型调用。

**限流与避免自我循环：** 每条记录默认 24 小时内不因同一证据重复复核；新的用户纠正或新工具证据可以提前触发。模型自己的维护建议、日志及写入成功通知不作为新用户对话再次提炼。同一目标版本与同一来源的处理只生效一次，无变化只推进复核时间，不新增版本。

**模型预算：** 候选提取、保存价值和更新建议尽量合并为一次后台模型调用。单次输入按原处理包 8000 单位上限计量，已有候选和旧记忆共同受预算限制；独立输出上限先按可配置的 2048 单位设置，在临时验收中按完整结构输出率与费用调整，不能据单次成功认定该额度足够。单次超时 30 秒，最多尝试 3 次，沿用 30/120 秒退避。空正文、结构无效、额度耗尽与连接失败均进入明确失败处理；合法空候选才算确实无内容。

**保存事务：** 候选或更新建议先持久化，再校验并应用；检查目标版本仍与输入一致，期间已发生其他更新时重新取证，不直接覆盖。一次纠正或替代涉及新旧记录、变更流水与作业回执时，应在同一数据库事务中完成，防止只让旧记录失效却没留下新版本。

**写入复核：** 保存后从库中核对新版本、当前有效版本、来源和状态。数据库已写成功但向量更新失败时记录“正文已保存、检索待修复”，由现有补偿机制重试；同步失败则保留待同步状态，不虚构两端一致。写入失败不回执为已入库，不依赖模型口头宣称成功。

### 完成条件与开关

新增完成条件：有价值内容无需保存指令或逐条确认即可处理；更新能追溯来源和旧版本；用户纠正、明确替代与待定冲突被正确区分；后台失败不漏记、不伪报成功；定期维护不制造自我循环；同包双端处理语义一致且只有指定端执行；更新结果真正参与后续回答与核查。原 B-R1—B-R11 收尾和原 B 最终样例仍必须通过，不能以新增模块替代旧缺口维修。

计划增加内容维护独立开关 `MEMORY_CONTENT_MAINTENANCE_ENABLED`（内容维护总开关，默认关闭）；它控制新增内容复核与更新作业，不改变现有冷热维护开关。**2026-10-11 下午已按此实现**：开关在 `agent_core/memory_switches.py`，网页与云端各在自己的装配处读它，用例见 `tests/test_memory_maintenance_jobs.py` 里的 `test_content_maintenance_is_its_own_switch`。逐轮候选与内容更新同样受新版总开关、指定处理端及权限规则控制。切换时停止产生新内容维护任务，让已认领事务安全结束，未执行作业保留，既有新版本不倒退；新版总开关关闭时原记录继续按旧兼容范围工作，新语义记录不会从关联旁路漏入。

内容维护费用独立记账，记录触发原因、任务状态、重试次数、变更数、拒绝原因和模型用量；运行日志只留引用与计数，不复制整段私人对话。所有新增默认值在临时验收中启用并检查，正式默认切换与部署不包含在本次文档更新中。
