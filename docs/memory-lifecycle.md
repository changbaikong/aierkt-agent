# 用户驱动的记忆生命周期

当前记忆系统优先跟随用户，而不是主动替用户推断长期人格或习惯。本版本不自动调用 LLM 做 Reflection，也不使用三维召回分数。

## 寿命规则（2026-10-12 收尾）

一条记忆留多久，由**用户原话**和内容性质一起定，判据只有一个入口（`agent_core/memory_horizon.resolve_lifetime`），提炼、落库、更新、双端四处共用。优先级从高到低：

| 顺序 | 情形 | 结果 |
| --- | --- | --- |
| 1 | 用户明说期限：「只限今天」「保留三天」「三天内有效」 | 按原话设置到期时间（天／周／月按实际单位换算） |
| 2 | 项目阶段约束：「这个项目暂时先不部署」「先设计，尚未实施」 | **长期保留**，等到被明确替代、取消或结束条件成立；不因为出现「暂时」就一天后失效 |
| 3 | 内容自己声明长期（`horizon=long_term`） | 长期保留；长期原则里出现「今天的事情今天做完」不会被关键词误判成当日状态 |
| 4 | 当天状态与情绪：「今天有点累」 | 沿用现有短期政策（一天） |
| 5 | 内容声明短期、其余情况 | 按短期政策；没声明就按长期，宁可多留一条 |

- 阶段约束与当天状态的区分看两件事：说的是不是某件具体的事（项目、部署、实施、验收…），以及用的是不是阶段性措辞（暂不、尚未、先、继续…）。「今天有点累」没有事项名词，不会被判成阶段约束。
- 短期记录落库时写 `expires_at`，长期记录不写；更新产生的新版本走同一条规则（`metadata.horizon` + `metadata.lifetime_basis` 一并保存并随双端同步传递）。
- 到复核时间只表示「该看一眼」，不表示内容已失效：没有新证据时不调模型猜测，也不生成新版本。

## 核对回执（2026-10-12 收尾）

候选与更新建议都带一份**由处理端生成**的核对回执：规则版本、内容与来源摘要、目标版本、逐项判断（有依据／无依据／不确定及对应原文）、依据引用和保留方式。

- 回执不接受模型或外部请求自带的「检查通过」；旧作业没有回执时先补检查再应用，不会默认为通过。
- 回执随记录附加信息（`metadata.evidence_receipt`）与队列作业（`memory_candidate_jobs.receipts`）持久保存；内容、来源、目标版本或规则版本一变，旧回执立即失效并重算。
- 逐项结果里只要有「无依据」或「不确定」，**整条暂不应用**：不自动删掉那一部分再保存，其他合格条目照常处理。理由里写明是哪一项、为什么。

## 什么算「有依据」（2026-10-12 收尾）

只认两类来源：用户自己说过的话（本轮或必要历史），和**成功**的工具回执。助手建议、模型解释、反复自检都不算。

- 数值按**值和单位**比：「三千元」和「3000元」是同一个值；「一律／统一／一样」里的「一」是词的一部分，不是数值。
- 审批／评审结论要单独找依据：固定字面（已获批准、评审通过）、「审批名词 + 结果词」（验收通过），以及**取得式同意**（已获上级同意、甲方认可、征得客户同意）都算结论；用户对别的事说「同意」不算。
- 实施结果同理：已实施、演练成功、已经上线，都要各自有出处；原话里的「尚未实施」不是「已完成」的依据。
- 条件、原因、适用范围也是信息：「以后全部这样做」不能从「今天先这样做」推出来。
- 换说法不算新事实：用／使用／采用／选择／决定／改为 之间互换，以及「预算八千」这类字段名 + 值，都按原话算；判断不了是不是换说法时记「不确定」，等新证据。
- 一个字的替换（方案甲 → 方案丙、方案 A → 方案 C）同样按新值核对。

## 生命周期

| 类型 | 默认行为 |
| --- | --- |
| `hot/active/message` | 保存当前对话消息；创建超过 24 小时后由维护任务迁移到 `warm`。 |
| `warm/candidate` | 候选记忆；连续 14 天没有被访问或确认时标记为 `expired`；双槽记忆另受自身 `expires_at` 约束。 |
| `warm/confirmed/fact` | 当前确认事实；冲突时旧事实归档到 `cold`。带 `expires_at` 的陪伴记忆到期即失效（不再"不因年龄自动过期"），不带 `expires_at` 的旧式 fact 仍不过期。 |
| `cold/archived` | 历史证据；普通问题不主动召回，历史问题或温层无结果时才参与检索。带 `expires_at` 的陪伴记忆按自身到期时间失效；不带 `expires_at` 的旧式记录按 180 天冷保留。 |

## 陪伴记忆（`save_memory`）：语义键 × 寿命政策

提炼器产出的陪伴属性记忆以**语义键为身份**，由 `save_memory` 落库，每条自带 `expires_at`：

| 语义键（身份，互斥维度） | 维度含义 | 同键保留 N 条 | 默认寿命政策 |
| --- | --- | --- | --- |
| `user.state.mood` | 即时情绪与压力 | 1 | 短（3h → 48h） |
| `user.task.current` | 即时工作/任务目标 | 3 | 短（3h → 48h） |
| `user.habit.schedule` | 作息与生活习惯 | 5 | 长（30d → 180d） |
| `user.preference.likes` | 情感倾向与好恶 | 5 | 长（30d → 180d） |
| `pet.relation.bond` | 与宠物的羁绊互动 | 5 | 长（30d → 180d） |
| 未知键（兜底） | —— | 3 | —— |

- **身份 = conflict_key = 语义键**：互斥只发生在**同一维度内**，不同语义键互不挤兑——同一轮对话里的情绪和任务可以同时存活。
- **寿命 = duration → 政策**：`instant`/`session` → 短寿命（3h~48h）；`habit`/`long_term` 或未知 → 长寿命（30d~180d）。`user.state.short` / `user.memory.long` 只是内部政策标签，不再当存储键。
- **权重 = importance（0~1）**：`expires_in = 政策下限 + importance × (政策上限 − 下限)`；缺省按 0.5（区间中点）。
- **confidence 职责不变**：≥ 0.85 落 `fact/confirmed`，否则 `candidate`。
- **同键替换**：新写入同语义键时，warm 层按 `created_at DESC` 保留最近 N 条，超出部分归档到 `cold`（与冲突替换一致）。
- 到期后由维护任务标记 `status='expired'` 并保留真实 `expires_at`，检索天然排除，再走两阶段清除。
- **被替换到 cold 的旧记录同样尊重自己的 `expires_at`**：归档时保留真实到期时间，维护任务按自身 `expires_at` 到期（几小时~几天，由 importance 决定），而不是等 180 天冷保留；不带 `expires_at` 的旧式记录仍走 180 天。

过期是两阶段操作：记录先变为 `expired` 并立即从检索授权中过滤，保留 30 天审计期；审计期结束后先删除当前 Qdrant point，成功后再删除 SQLite 行，FTS5 通过触发器同步删除。向量删除失败时保留主记录并由下一次维护任务补偿。

## 记忆强化

每次记录被最终选入上下文，SQLite 更新 `last_accessed_at` 和 `access_count`。这些字段首版用于观察和后续策略评估，不改变当前 RRF 检索排序。

新增元数据包括 `importance`、`expires_at`、`purge_after`、`retention_locked` 和 `deletion_reason`。用户明确要求保留的记录可设置 `retention_locked`；用户明确要求忘记时，应调用显式删除流程。

## 后台维护

`MemoryMaintenanceWorker` 不会在构造时自动启动。应用需要显式调用 `start()`，退出时调用 `stop()`。默认每 60 秒执行一次：

1. 迁移超过 24 小时的 hot 消息。
2. 标记已到 `expires_at` 的陪伴记忆为 `expired`——无论还在 warm，还是已被替换归档到 cold，都按各自真实 `expires_at` 到期。
3. 标记超过 14 天未访问的 warm candidate，和达到 180 天冷保留期的 cold archived 记录（仅限不带 `expires_at` 的旧式记录）。
4. 删除已过审计期记录的向量和主表行。

所有层迁移都沿用”先写目标 collection，再删除旧 collection”的一致性流程。旧式 confirmed fact（不带 `expires_at`）仍不会被这套时间维护任务自动删除；陪伴记忆则到期即失效——即使被替换归档到 cold，也按自身 `expires_at` 清除，不会在 cold 里滞留 180 天。
