# 主 Agent 上下文与联网搜索问题清单

## 调查范围

本次只检查主聊天、联网搜索、记忆库、上下文编排、云端/本地协作、后台任务、子代理和代码任务。**排除场景对话区**。本报告是问题审计和改造顺序建议，没有修改运行代码、配置或线上记忆数据。

## 结论先说

现在的问题不是“搜索提示词写得不够好”，而是一次用户请求会被拆成几条彼此不共享上下文的链。搜索一旦被判定为需要，主循环会跳到独立搜索回答器；它拿到的是当前问题、外部材料和很短的近期历史，拿不到正常回合里已经组装好的角色、长期记忆、较早历史、图片和一次性约束。因此“同一个主模型”只说明调用接口可能相同，不说明模型看到了同一份输入。

记忆链也有两个独立问题：提炼范围本身主要保存陪伴属性，不保存项目决策及其原因；搜索回答又绕过了正常记忆上下文。于是“记忆库里没有有用内容”和“有内容但本轮没有用上”会同时发生。

云端和本地目前是同一份代码和同一套服务状态，不能据此认为是一条完整的双端流程。网页只上传当前一问一答给云端，云端提炼也不接收历史；本地默认关闭提炼和维护。两端都没有承担“完整编排、出错接替、去重回写”的统一职责，所以把功能固定切给某一端会继续放大断点。

## 已确认的核心问题

### A. 联网搜索把主回答链切断

> **独立验收状态（2026-10-10）**：搜索接回主回答链的核心改造已成立，但 A 完整验收未通过。
> 六项收尾缺口涉及后续证据合并、核查背景、失败收口、辅助预算、用量结算和答案全文核查，见 [A 验收报告](2026-10-10-search-mainloop-acceptance.md)。
> 下列 A1—A8 保留为改造前的问题记录；当前逐项状态以验收报告为准。B 已出 [维修计划](superpowers/plans/2026-10-10-memory-repair.md)，尚未实施；C—E 仍未处理。

**A1. 搜索是硬分叉。**

搜索门判定“需要搜索”后直接进入独立搜索流程，不再经过普通模型工具循环。普通回合中的角色、记忆和完整历史已经组装好了，却没有传入搜索回答器。

触发：问题被判定为需要联网。

影响：搜索回答看起来像临时检索机器人，和用户长期对话脱节。

状态：代码确认，并用替身模型在真实会话链复现。

**A2. 搜索回答器的输入过窄。**

它只接当前问题、外部材料和最近四条普通用户/助手消息；长期记忆、较早历史、角色上下文、当前图片、一次性指令及其他工具结果都会丢失。

影响：无法判断“这个问题对用户的项目意味着什么”，也无法利用以前已经做过的选择。

状态：代码确认。

**A3. 同一个模型不等于同一个上下文。**

每次模型调用都只看调用方传入的消息。搜索回答器即使复用同一模型、同一 Provider，也不会自动继承主回合的 system、记忆或工具结果。

影响：把“已经接入主 LLM”误当成“已经融合记忆”，导致架构判断失真。

状态：由调用边界和替身复现共同确认。

**A4. 搜索材料没有独立的任务提炼层。**

搜索摘要和网页前段被直接当作事实材料交给回答整理器，最多保留有限条目并做前截断；没有先按用户目的抽取“支持什么、缺什么、冲突在哪里”。

影响：材料多但答案不聚焦，长网页中的限制条件可能被截掉，模型只能把片段重新拼接。

状态：代码确认；具体网页截断造成的漏条件属于设计风险，仍需用代表性网页验收。

**A5. 回答整理器强制输出“关键依据”。**

固定提示要求“再补一到三条关键依据”，但没有要求筛选用户真正有用的结论、说明与用户记忆的关系或压缩重复信息。审查器也只看证据是否支持、是否冲突和是否泄露过程，不看答案是否解决了用户目的。

影响：截图中出现的长段官方宣传、兼容说法、免费说法和未确认信息被混在一起；“关键依据”更像报告口吻，容易让人感觉 Agent 把内部依据展示出来。

状态：代码确认。当前证据不足以称为内部思维泄露，更准确的说法是提示词把证据说明写成了面向用户的固定段落。

**A6. 搜索后的最终重写没有再次审查。**

搜索流程最多核查一次并重写一次；重写后的文本不再经过同等级证据检查。普通最终回答清洗也没有统一覆盖这条路径。

影响：最后一次改写可能重新引入未经支持的表述，且搜索回答和普通回答的语气、简洁度、来源契约不同。

状态：代码确认。

**A7. “不搜索”决定在本轮基本不可纠正。**

当入口判断不需要搜索时，搜索工具会被屏蔽；后面的普通最终复核在已有意图状态时又会跳过。因此入口误判、轻量模型判断失败或用户问题表达含糊时，本轮没有统一的补救点。

状态：代码确认。

**A8. 搜索的观测口径和普通回答不一致。**

搜索流程有实际次数上限，但模型用量记录为零；首字时间从答案生成和核查后才开始计时；搜索结果还按最后三十二字符分段发布，普通回答则实时生成。

影响：监控会低估搜索成本，前端体验和耗时指标不能直接与普通对话比较。

状态：代码确认。

### B. 记忆提炼和召回本身不支持当前目标

**B1. 自动提炼的范围不对。**

提炼提示明确限制在情绪、作息、喜好、宠物关系和当前任务五类陪伴属性；项目决策、决策原因、完成状态、失败经验、主题关系等不会稳定进入记忆。

影响：即使搜索回答正确读取了记忆，也可能找不到“用户为什么选这个架构”和“哪些方案已经放弃”。

状态：代码确认。

**B2. 云端提炼只看到当前一问一答。**

网页同步队列上传的是当前用户文字和当前助手回复，不带完整历史；云端 worker 也不向提炼器补历史。

影响：云端无法从多轮对话中识别决策形成过程，云本地两端也无法靠“同一套提炼代码”弥补输入缺失。

状态：代码确认。

**B3. 记忆召回只按当前文字检索。**

查询没有先把“这个、上次、那个方案”等代词改写成当前任务，也没有根据对话目标生成检索问题。

影响：用户已经在前文说明背景时，后一句短问句很难召回正确记忆。

状态：代码确认。

**B4. 冷记忆和关联记忆召回过于保守。**

冷区只在历史型问法或温区为空时查询，没有主题关系扩展；相关主题不会因为可能改变答案而进入候选。

影响：跨项目经验和早期关键决策几乎不会自然“发散”到当前问题。

状态：代码确认。

**B5. 召回排序把确认状态和时间放在任务价值之前。**

排序偏向 confirmed、近期热窗口和温区内容，不判断一条记忆是否真的会改变当前答案。

影响：一条“提炼得很确定但作用很小”的偏好，可能挤掉一条“状态未确认但与当前架构直接相关”的决策。

状态：代码确认。

**B6. 记忆元数据在召回时被压平。**

保存时有原始用户话、助手话、类型和可见性等信息，召回输出主要只保留正文和简单标签。

影响：回答器不知道这是事实、计划、偏好、假设还是失败经验，也不知道结论为什么成立，容易把计划当成已完成事实。

状态：代码确认。

**B7. 普通历史和热记忆重复占用上下文。**

同一段近期内容既以对话历史出现，又以热记忆出现，检索预算没有做去重。

影响：有效上下文变短，越到长对话越容易把真正相关的温冷记忆挤出去。

状态：代码确认。

**B8. 长温记忆可能被整条过滤。**

超过约八百字的温区原话在进入检索时会被过滤，而不是先摘要或按相关片段切分。

影响：重要的长讨论可能完全不可见。这个阈值是否在真实数据中已经造成具体漏召回，还需用样本验收。

状态：代码确认，实际影响待验。

**B9. 可见性把“自动记忆”隔离成模块级。**

自动提炼默认按 owner、channel、conversation、module 隔离；另一个手动保存事实接口默认 shared。两类记忆的可见范围和使用语义不一致。

影响：用户以为“我的记忆库”是全局的，实际可能只在当前模块或当前会话可见。

状态：代码确认。

**B10. 业务结果没有稳定的沉淀入口。**

后台任务结果、代码任务结果和 steward 进度被排除在自动提炼之外；排除状态播报本身合理，但重要业务结论没有另一条统一的“结论、依据、状态、后续动作”写入路径。

影响：主聊天无法在下一次任务中复用已经完成的工作。

状态：代码确认。

### C. 上下文编排没有一个统一的优先级决策者

**C1. 主回合、搜索回合、收口回合各自决定上下文。**

普通回合、搜索回答器和预算收口使用不同的消息集合与截断规则，没有一个统一编排结果说明“本轮必须保留什么、可以舍弃什么”。

影响：同一问题换一个分支，模型看到的背景会变，回答质量不可预测。

状态：代码确认。

**C2. 长历史的收口策略只裁工具结果。**

预算不足时会逐级压缩工具结果，但普通历史没有按任务价值摘要；历史过长时可能还没真正完成一次模型调用就进入失败或不完整收口。

状态：代码确认；需要用超长真实历史补一次端到端验收。

**C3. 记忆优先级不是任务优先级。**

系统目前用热、温、冷和 confirmed 等存储属性近似回答优先级，却没有明确区分“直接约束、已做决策、当前任务事实、可选背景、探索性关联”。

影响：优先级错误不是模型不会总结，而是它收到的候选集合已经排错了。

**C4. 角色、记忆、工具规则和一次性要求没有统一契约。**

普通主链会把它们放进 working context；搜索、定时任务、子代理、代码执行器各自重新拼提示，导致角色风格、记忆使用和输出要求漂移。

状态：代码确认。

### D. 其他会分裂流程的入口（排除场景对话区）

**D1. 快捷播放和导航会吞掉复杂复合请求。**

播放判断只要句子中有一句命中，就可能整轮提前返回；导航目的地匹配对“到后面”的文本较贪婪。比如“现在在放什么歌，结合我的喜好再推荐两首”会只返回播放器摘要，“导航到广州塔，结合我的情况推荐路线”会把后半句并进目的地。

影响：用户同时提出的记忆分析、推荐或解释没有机会进入主回答。

状态：本地规则复现。天气混合请求已有保护，不能把所有快捷入口都说成必然误吞。

**D2. 定时任务是裸循环。**

定时任务使用独立提示、任务文本和受限工具，不带聊天历史、个人记忆、统一角色或搜索门；完成后完整结果在任务存储中，聊天回执只保留最多六十字。

影响：后台查到的内容不能自然接回主聊天，也没有来源结构，用户只看到通知开头。

状态：代码确认。

**D3. 子代理只拿任务文字和手抄背景。**

子代理有独立上下文是合理的，但当前没有标准化传递“与任务有关的记忆、硬约束、用户偏好、证据保留规则”；回复还会截断且不带结构化来源。

影响：主模型只能猜哪些背景重要，结果难以可靠综合。

状态：代码确认。

**D4. 代码任务的记忆接线没有生效。**

启动时给代码 Provider 挂了记忆检索器属性，但当前 Harness 执行器构造的任务提示只包含工作目录边界、任务目标和总结要求，没有消费这条检索器。

影响：代码任务是否有背景完全依赖提交时手写进目标的文字；不能说它完全没有任何背景，但可以确认“记忆检索器未参与执行”。

状态：代码确认。

**D5. 代码任务回执再次截断并绕过主综合。**

代码执行器消息或摘要只保留前四百字，后续用省略号；非代码结果也由独立措辞器直接写入历史，没有统一主模型把目标、改动、证据和风险综合成对话回答。

状态：代码确认。

**D6. 审批恢复使用旧快照。**

恢复会沿用暂停时的会话快照，不重新检索新记忆或重新编排上下文；当前图片在快照里只保留占位，恢复时无法重新查看原图。

影响：用户在等待确认期间补充的新背景不会进入恢复回答，涉及图片的审批任务可能失去关键输入。

状态：代码确认；是否所有恢复入口都漏掉云端入队和提炼，需要补一条端到端测试确认。

**D7. 新旧搜索路径并存。**

新搜索门、旧研究范围确认、legacy/model routing、音乐专用路径仍可能按条件进入不同链；旧路径保留完整 working context，新路径使用独立 composer，来源和润色契约也不同。

影响：相似问题可能出现不同的上下文、来源位置和回答口吻。

状态：代码确认；不能把所有显式平台搜索都断言为当前默认旧路径。

**D8. 命令行入口没有网页的提炼、云同步和维护启动。**

命令行复用主 loop 和搜索门，但主要只写原始对话；历史在进程内，重启后普通历史消失，且默认 channel 与网页不同，自动模块记忆会进一步隔离。

影响：同一用户从网页和命令行继续问，看到的记忆背景可能不同。

状态：代码确认。

**D9. 确定性快捷路径和普通回答的来源契约不同。**

搜索新路径返回结构化来源，旧路径可能把来源拼在正文或尾注；前端已经兼容两种格式，但后端仍有多种输出形状。

影响：来源展示可以做成小气泡，但长期依赖文本尾注会继续让正文、来源和历史记录相互耦合。

状态：代码确认；前端并非完全不支持结构化来源。

### E. 云端与本地的真实关系

**E1. 两端代码和服务状态一致，不代表流程已经对齐。**

只读对照显示两端关键服务运行、相关代码哈希一致、温冷区计数相同；这只能说明部署版本和粗粒度状态相近，不能证明逐条记忆、请求输入和回答上下文相同。

**E2. 当前模式是“本地记录、云端异步提炼”，不是双端互相接替。**

本地默认关闭提炼和维护，网页只把当前一问一答排队上传；没有证据表明云端失败时本地会自动接替，也没有统一去重和回写协议。

**E3. 两端都沿用了相同的输入缺陷。**

云端拿不到历史，本地搜索分支也拿不到已组装的记忆；把搜索或提炼固定放到某一端，不会修复“请求进入分支时上下文已丢失”的根因。

**推荐边界**：云端和本地都实现同一份“完整回合契约”（任务背景、相关记忆、当前历史、工具证据、来源和状态）；正常情况下只由一端处理，另一端可在故障时接替；用回合编号和内容指纹去重，结果回到同一主回答链。不要把一端固定成搜索端、另一端固定成记忆端。

## 根因归纳

1. **上下文在分支入口被重新拼装**，没有唯一的回合上下文对象。
2. **记忆保存模型和回答使用模型不匹配**：保存偏陪伴属性，回答需要项目决策、原因和状态。
3. **能力返回的是半成品或最终话术**：搜索、后台任务、子代理、代码任务都可能直接产出一段独立回答，没有统一交给主 Agent 综合。
4. **优先级由存储位置、时间和确认状态代替**，没有由当前任务目标决定。
5. **云端、本地和旧新路径各自维护输入、输出和观测口径**，所以“同模型、同代码、同计数”仍会出现不同体验。

## 改造顺序和验收标准

### 第一阶段：先修回合边界

建立唯一的回合上下文：当前任务目标、角色、一次性约束、对话历史、直接记忆、关联记忆、工具结果、来源和运行状态都由主编排器生成。搜索、后台任务、子代理和代码任务只能接收这个上下文的任务化子集，并必须返回结构化证据和状态，不能直接替主聊天决定最终话术。

验收：同一个问题分别走普通、搜索、恢复和后台回执，主模型都能看到同一条任务背景；切换 Provider 不改变背景集合。

### 第二阶段：修记忆内容和优先级

增加事实、决策、偏好、经验、开放问题、假设等类型；重要决策保存原因、目标、状态和关联主题。检索先由当前任务生成查询，再按“直接约束→当前决策→相关事实→可选背景”排序，保留元数据并去掉与历史重复的内容。

验收：给出一个曾讨论过的架构问题，回答必须指出相关旧决策、它的原因和当前状态；把旧决策标成假设时，回答不能把它说成事实。

### 第三阶段：统一搜索和证据整理

搜索只负责找证据、读取原文和报告覆盖情况；主编排器负责把记忆与证据合并，再由唯一回答器生成简洁答案。证据审查应覆盖最终文本，来源使用结构化字段，依据只在能帮助用户判断时展示。

验收：同一搜索材料分别在有记忆和无记忆时，答案能明确体现差异；最终答案没有材料堆叠、未确认宣传和内部流程口吻。

### 第四阶段：收拢旁路

复合播放/导航、定时任务、子代理、代码任务、审批恢复和命令行都统一使用回合契约；纯事实快捷回答可以保留，但只有在确认没有第二个意图时才能提前结束。恢复时重新计算可变的记忆和背景，图片任务保留可重新读取的受控引用。

验收：复合请求不丢第二个意图；定时任务完整结果可展开并带来源；代码任务能看到明确传入的相关记忆；恢复前后的新背景按规则生效。

### 第五阶段：云本地双端对齐

两端共用上下文契约、记忆类型、检索排序和结果 schema；用主端/接替端状态、幂等回合编号和失败转移实现接管。不要继续用“云负责搜索、本地负责记忆”之类固定能力切分。

验收：任一端单独处理同一回合时，输入摘要、证据集合、最终回答结构和记忆写入结果一致；重复投递不会重复写入；一端故障后另一端能从同一回合状态接续。

## 证据边界

本报告把“代码已确认”“替身或规则已复现”“设计风险待验”分开写。没有把冷记忆过期查询、恢复后所有云同步漏失、所有快捷请求必然误吞等尚未复现的情况写成既成事实，也没有包含 IP、口令、密钥或真实私人对话。
