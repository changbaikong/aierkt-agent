# 云端记忆后台 + 本地读取改造计划

现状：本地 `data/memory_records.db` 是权威库（1371 条）；云端已有一套能跑的提炼链路
（`agent-memory.service` + `agent-ingest.service` + Qdrant server），但它写死在一个默认会话里、
只做单向接收。两边已经开始分叉（云端 1373 条、本地 1371 条，层分布也不同），目前没有任何对齐机制。

目标形态：**本地负责记录与读取，云端负责提炼、轮转、维护，每 10 分钟双向同步一次。**

---

## 一、先定下来的几个设计选择

写在这里免得后面反复讨论。每条都是「选了什么 + 为什么不选另一个」。

1. **变更编号用云端单调递增整数，不用时间戳。** 新表 `memory_changes`，主键自增。
   时间戳在批量同秒写入时会撞号，本地就无法判断谁先谁后 —— 验收项里明确有「同时间记录」这一条。
2. **同步器跑在本地 web_api 进程内，不另起进程。** 本地向量库是嵌入式模式、单进程独占目录，
   另起一个同步进程会互相抢 `data/memory_vectors`（云端已经踩过一次这个错）。
3. **本地自己按对话原始时间算过期，不等云端下发。** 读取路径本来就有到期过滤，
   所以断网期间到期的记忆也立即可用不了，不会因为同步断了就复活。
4. **删除一律走归档，不物理删。** 与项目既有惯例一致（归档不删）；
   只有云端下发 `expired` 且已过 `purge_after` 的记录才真正清理。
5. **上传队列落本地 SQLite，不用 JSONL。** 需要事务、需要抗强退、需要整轮精确去重，
   文件追加式队列做不稳。这条修正了当前 `scripts/push_memory_to_cloud.py` 的做法。
6. **云端接收口必须收真实的账号/角色/会话。** 现在它写死一个默认会话，
   这正是第 5 条要改的地方。

## 二、十项任务

### 1. 调整职责边界

- 本地加两个开关（照 `SEARCH_GATE_ENABLED` 的写法）：`MEMORY_EXTRACT_ENABLED`、
  `MEMORY_MAINTENANCE_ENABLED`，默认都开；云端模式下在 `.env` 里关掉。
- 关掉的只是「本地提炼」和「本地轮转维护」，**本地读取、本地写入、本地向量检索全部保留**。
- 云端只跑接收、提炼、维护三个服务，不跑 `web_api` 聊天主链路、不跑前端。
- 记忆分类（hot/warm/cold）、保留条数、过期规则一个字不改，只是执行地点搬家。
- 验收：关开关后本地日志不再出现提炼与维护记录；同一轮对话在云端被提炼出来。

### 2. 可靠上传

- 对话落账后（现在挂提炼的那个位置）改为写一条待上传记录到本地新表 `memory_upload_queue`：
  用户原话、最终回复、原始时间、账号、角色、会话归属，`turn_id` 唯一约束。
- 云端接收口按 `turn_id` 去重，重复上传直接回「已收过」，不生成第二条记忆。
- 彻底删掉「拿记忆行反推成对话再提炼」的旧做法 —— 那会把已经提炼过的东西重炼一遍。
- 验收：同一轮 `turn_id` 连发 3 次，云端只入库一次。

### 3. 同步时机

- 进程启动后立刻同步一次；运行期间每 10 分钟跑一轮「先上传、再拉取」。
- 用一把锁保证同步任务不重叠，上一轮没跑完就跳过这一轮，不排队。
- 正常退出最多等 5 秒补传；强退或休眠留下的未传内容靠队列持久性，下次启动自动补。
- 同步**不阻塞聊天**：入队是本地事务、毫秒级，实际网络请求在后台任务里做。
- 验收：断网期间正常聊天不卡；恢复网络后下一轮把积压全部传上去。

### 4. 修复云端任务状态

- 队列项状态区分三种：`stored`（提炼出记忆并入库）、`empty`（确实没值得记的）、
  `failed`（调用或解析出错）。**失败绝不能记成完成** —— 现在失败和空结果都叫 `empty`，这是真 bug。
- 失败重试间隔 30 秒 → 2 分钟 → 10 分钟，最多 5 次；耗尽后保留任务并写告警日志。
- 提炼结果先落库再推进水位，中途重启不会重复生成记忆。
- 验收：把 key 改坏，观察状态是 `failed` 且按间隔重试；改回后自动补完。

### 5. 保留时间与归属

- 上传带上真实 scope（账号/角色/会话），云端按原样落库，不再塞进默认会话。
- 记忆寿命从**原对话发生时间**算，不用云端收到的时间。
- 迟到的旧情绪不能覆盖较新的同槽位情绪：写库时比对原时间，旧的直接归档。
- 后台维护每 60 秒、向量补偿每 30 秒（现有节奏不动）。
- 验收：上传一条三天前的情绪，检查它没有顶掉今天的同槽位记忆。

### 6. 本地下行更新

- 云端每次增/改/过期/删都写一条 `memory_changes`（自增编号 + 记录 id + 动作 + 载荷）。
- 本地存一个「已应用到第几号」的水位，按编号顺序合并，**应用成功才推进水位**。
- 首次接入或水位对不上时用完整快照：先校验，再合并云端管理的记录。
- 本地正在用的库**绝不直接覆盖**：合并走 SQLite 事务，快照先落到临时文件。
- 验收：人为把水位退回去，重放一遍，结果幂等（条数不变）。

### 7. 读取与向量状态

- 记忆被本地读取时，上传去重后的访问记录（同一记忆同一分钟只算一次），
  让云端的「多久没被用过」判断准确。
- 云端生成的向量随变更回传，本地**装好之后才标记可用**；没装好时退回文字检索，功能不中断。
- 到期记忆即使还没同步也不能用 —— 本地读取过滤已经保证了这条。
- 验收：断开向量回传，检索仍能靠文字命中；恢复后向量标记转为可用。

### 8. 接口与保护

- 云端四项接口：`/api/memory/sync/events`（收上传）、`changes`（拉变更）、
  `snapshot`（取快照）、`status`（看状态）。
- 上传接口返回 200 才代表**已持久保存**，本地收到确认才推进上传水位（现在只是写了个文件就返回）。
- 快照响应带上变更编号和校验值。
- 全程走 HTTPS + 身份验证，并且**限定账号只能访问自己的数据**（现在只有一个全局口令，不区分账号）。
- 验收：用错口令、越权访问别的账号，都应被拒。

### 9. 首次接入

- 先备份两端现有库（本地已经有一份 10-09 的快照在服务器上，还要再加一份本地的）。
- 核对差异，**以本地库为基线**；云端独有的记录保留并单独列出来，不静默丢。
- 历史记忆直接迁入，**不重新提炼**（这也是第 2 条要删掉旧做法的原因）。
- 切换后新对话走上传队列；断网时继续用本地库；上传失败不推进水位。
- 验收：产出核对清单，逐条说明「本地独有 / 云端独有 / 两边都有但状态不同」。

### 10. 验收与上线

- 先在独立测试库跑这些场景：正常同步、断网补传、重复上传、同秒记录、
  处理中重启、快照与聊天并行、到期处理、账号隔离。
- 再跑整套系统测试（现有 runner，不用裸 pytest）。
- 统计四项数字：排队等待时间、提炼耗时、失败率、费用。
- 全部过了才部署；保留一个回退开关（关掉同步就退回纯本地模式）。
- 补使用说明和经验记录。

## 三、还没定的

- **HTTPS 怎么来**：直接上证书（要域名），还是走 SSH 隧道不开公网端口。后者更安全，
  代价是本地要常驻一个隧道进程。
- **费用口径**：提炼按次调模型，一天 144 次轮询不都产生请求，但大概量级要先算清再上。
